A Futuristic Gaming Platform Built with AWS & DevOps

CI License: MIT Tests Coverage

GameHub is a portfolio project that combines a futuristic gaming interface with a containerized Node.js backend and a MySQL database — all runnable locally with one command. It demonstrates how frontend applications, backend APIs, container networking, reverse proxies, databases, tests and CI pipelines work together.

The project is being evolved into a production-style application: automated CI/CD, infrastructure as code on AWS, monitoring, and Kubernetes (local kind cluster + Argo CD).

Status — Phase 8 complete (2026-10-19): tested, CI'd, game-y, playable and live on AWS, observable, runnable on Kubernetes, hardened — and documented. 84 automated tests, a Cognito sign-in gate with working account deletion (GDPR art. 17, in the app rather than in a policy document), a bilingual privacy notice, an SBOM + image scanning in CI, deploys that only run on a green CI for the exact commit, a measured t3.micro load test, and the whole write-up published at /learn/ as a site and a PDF. All described as CloudFormation and deployed by keyless GitHub OIDC, on a custom domain with an ACM certificate.

Live demo: https://gamehub.worldofvpc.online — create an account (email confirmation), sign in, and play. The landing page is public; the catalogue and the games require a signed-in player.

Documentation: the step-by-step write-up, the ADRs and the runbook are published as a small static site at https://gamehub.worldofvpc.online/learn/, with the whole guide as a printable PDF, and every claim in it traceable to a commit and a CI run.

✅ Completed (Phase 5 — observability)

  • Structured request logs: nginx emits JSON access logs (status, uri, request_time, upstream_time) — CloudWatch parses them without regex guesswork
  • CloudWatch agent on the host: ships those logs plus container stdout to /gamehub/prod/nginx-access and /gamehub/prod/app (7-day retention set by the template), and host mem/disk/swap metrics into the CWAgent namespace — installed by user-data, no manual setup
  • Metrics derived from logs (AWS::Logs::MetricFilter): request count, 5xx count, and API latency as a numeric extraction ($.request_time) for p50/p99 — nginx already knew the numbers, so the app is not instrumented with an extra library to repeat them
  • External availability check: EventBridge runs a small Lambda every 5 minutes against the public CloudFront URL and /api/health; its log line becomes the SyntheticSuccess metric — a synthetic check without the CloudWatch Synthetics price tag
  • Eight alarms into one SNS topic: synthetic availability (TreatMissingData: breaching — silence is a failure), 5xx count, API p99 latency, instance status, CPU, CPU credits, memory and disk. Host-metric alarms treat missing data as notBreaching, because a stopped agent is not an outage
  • One dashboard (gamehub-prod): availability, requests vs errors, latency percentiles, host pressure, and two live log tables (recent 5xx, backend tail)
  • SLOs with error budgets (docs/slo.md): 99.5 % availability and p99 ≤ 1.5 s over a rolling 30 days, with the measurement method for each — and an explicit list of what is not claimed, because a single-AZ t3.micro cannot honestly promise it
  • Runbook (docs/runbook.md): one section per alarm with the exact SSM/Logs-Insights commands to confirm the cause, plus the revert-to-roll-back path
  • Verified live, not assumed: the agent's metric dimensions were read back from list-metrics and then written into the template — an alarm with the wrong dimension set sits in INSUFFICIENT_DATA forever

✅ Completed (Phase 6 — local Kubernetes + Argo CD GitOps)

  • Real cluster, no bill: a single-node kind cluster (k8s/kind-config.yaml) with the same images the Compose stack builds, side-loaded into the node (make kind-up)
  • Deployments and a StatefulSet: frontend and backend run 2 replicas each with maxUnavailable: 0 rollouts; MySQL is a StatefulSet with a volume claim template — a Deployment would give the database a random name and two pods fighting over one data directory
  • Probes with consequences: liveness on /api/health (no database), readiness on /api/ready (database) — a DB outage stops new traffic instead of restarting every pod
  • One source of truth for the seed: db/init.sql is rendered into a ConfigMap by scripts/build-k8s-dbinit.sh, and CI fails if the copy drifts from the source
  • Least privilege, measured rather than assumed: the backend runs as the unprivileged node user with drop: ALL; nginx keeps exactly the five capabilities its root master process needs — the first attempt at drop: ALL produced CrashLoopBackOff with chown(...) failed (1: Operation not permitted), which is why the list is now written down with a reason
  • GitOps with Argo CD (k8s/argocd/application.yaml): automated sync with prune and selfHeal, so the merge to main is the deploy and a manual kubectl edit is reverted by the controller
  • Verified like the rest of the project: the same scripts/smoke.sh runs against the cluster's NodePort (8081, so Compose on 8080 keeps working) and passes — 12 games served from the StatefulSet through the nginx proxy
  • CI covers it: a manifests job validates every manifest against the Kubernetes schema (kubeconform) and checks the generated ConfigMap for drift

✅ Completed (Phase 7 — security hardening & GDPR)

  • Erasure that is implemented, not promised: DELETE /api/me deletes the player's rows and their Cognito identity in one action from the account page. A partial result is reported as a partial result (502), never as success
  • The account page is the GDPR surface: it is the access/portability answer (identity + every stored row, copyable as JSON) and it carries the deletion control — one page, three of the four rights, no support email
  • A bilingual privacy notice (frontend/privacy.html): a data inventory with purpose, legal basis and retention per item — including the 7-day access logs, which are personal data too
  • One AWS call, signed by hand: account deletion needs cognito-idp:AdminDeleteUser, so the backend fetches IMDSv2 credentials and signs the request itself (SigV4, node:crypto) — no AWS SDK, no long-lived keys, and the signature is asserted field by field in the test suite
  • Least privilege on the identity: the instance role's inline policy allows that one action on one user-pool ARN, not CognitoPowerUser on *
  • Data minimisation in the schema: one personal_bests row per (player, game) with GREATEST() on conflict — the best score, no play history — keyed by the Cognito sub, so the database holds no email address
  • Migrations with a ledger (scripts/migrate.sh, db/migrations/): db/init.sql only runs on an empty volume, so schema changes ship as checksummed, idempotent migrations; a rewritten migration is refused
  • Supply chain in CI: SPDX SBOM (syft) kept as an artifact, Trivy against the built image as well as the filesystem, npm audit, gitleaks over the full history, and Dependabot for npm, Actions and base images
  • Deploys are CI-gated: the deploy workflow runs on a successful CI run for the exact commit (never a later, untested tip of main) and finishes with a post-deploy smoke test against the public URL: the app shell, the documentation site and its PDF, a 401 from every protected route without a token, and — signing in as a dedicated smoke identity — the 12 catalogue entries, the game details, and an identified player from /api/me

✅ Completed (Phase 8 — /learn documentation site, PDF, load test)

  • A documentation site generated from the repository: scripts/build-learn.js (dependency-free, Node built-ins only) renders README.md and every docs/*.md into learn/ — a landing page, one page per document, a print guide, and a hand-written Markdown renderer with GitHub-style table support

  • A CI drift check: the generated site is committed, so the manifests job regenerates it and fails on any diff, and asserts that every document has a page — a generated artifact that is never checked is an artifact that goes stale

Request flow

  1. A user opens GameHub in the browser.
  2. Nginx serves the static frontend files.
  3. JavaScript sends API requests to the frontend's /api/ path.
  4. Nginx forwards those requests to the backend container.
  5. Express processes the request and queries the MySQL container over the private Docker network.
  6. The backend returns JSON, which the frontend uses to render game cards.

Important: The browser accesses the frontend through port 8080. The Nginx container communicates with the backend using Docker networking, and the backend port is not published to the host — the database runs as a local MySQL container (managed by hand, not by IaC — see the note in the Database section).

Prerequisites

  • macOS or Linux
  • Git
  • A Docker runtime + Docker Compose (on this Mac: Colima — start it with colima start)

No configuration needed. The stack ships with working local defaults: a MySQL container is seeded automatically from db/init.sql on first start.

make ps               # container status (healthy?)

make smoke            # re-run the end-to-end checks
make test             # backend unit + integration tests (needs MySQL)
make test-frontend    # game-engine, mapping-contract and auth tests (Node only)

☁️ Deploy to AWS

Everything is CloudFormation in infra/ — six small stacks, each one a single command. Stack outputs feed the next stack, so there is no spreadsheet of ids to copy by hand.

export AWS_REGION=eu-central-1
export ZONE_ID=<your route 53 hosted zone id>   # aws route53 list-hosted-zones

# 1. Cognito user pool + app client
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-cognito --template-file infra/cognito.yaml \
  --parameter-overrides Stage=prod

# 2. Certificate for the custom domain. CloudFront only accepts certificates
#    from us-east-1, hence the separate stack and the separate region. DNS
#    validation happens inside this stack — there is nothing to click.
aws cloudformation deploy --region us-east-1 \
  --stack-name gamehub-dns --template-file infra/dns.yaml \
  --parameter-overrides DomainName=gamehub.worldofvpc.online HostedZoneId="$ZONE_ID"

# 3. S3 + CloudFront (deployed first without an API origin)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-site --template-file infra/site.yaml \
  --parameter-overrides \
    Stage=prod \
    CustomDomain=gamehub.worldofvpc.online \
    CertificateArn=<gamehub-dns CertificateArn output> \
    HostedZoneId="$ZONE_ID"

# 4. EC2 host running the compose stack (needs the CloudFront domain)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-backend --template-file infra/backend.yaml \
  --parameter-overrides \
    Stage=prod \
    CognitoUserPoolId=<pool id> \
    CognitoClientId=<client id> \
    SiteOrigin=<https://cloudfront domain> \
    DbPassword=<16+ chars> RootDbPassword=<16+ chars>

🗄️ Database

GameHub uses MySQL 8.4 in a container, seeded automatically from db/init.sql on the first start of an empty volume. This makes a fresh clone reproducible with no cloud account and no secrets — and the deployed stack runs the same container on the EC2 host, so there is exactly one database setup to reason about. Moving to RDS (multi-AZ, automated backups, managed patching) is a deliberate cost/ops trade-off left for a later phase rather than a claim made here.

Reset to a clean seeded state any time with make db-reset.

Migrations

db/init.sql runs once, on an empty data volume — which is correct for a fresh clone and wrong for a live database. Schema changes therefore ship as migrations:

./scripts/migrate.sh            # apply everything pending
./scripts/migrate.sh --status   # what is applied, what is pending

Each file in db/migrations/ is recorded in a schema_migrations ledger with a checksum. A migration that was applied and then edited is refused, because the database that ran it is no longer described by the file. The runner reaches MySQL through docker compose exec on a host and through the mysql client in CI (MIGRATE_VIA), so the same script runs in both places. It is also part of the deploy: the rollout brings the schema up to date after the containers start.

The frontend retrieves game records dynamically through the Express API rather than relying entirely on hardcoded game cards.

🔐 Security Practices

  • No secrets required for local development — compose defaults live in the private Docker network; nothing sensitive exists in the repo.
  • .env is excluded from Git and from image builds (backend/.dockerignore); backend/.env.example documents every variable.
  • The backend runs as a non-root user and reads all configuration from environment variables (12-factor).
  • The API port is not published to the host — only nginx on :8080 is reachable.
  • npm ci from a committed lockfile; the dependency tree is audited (0 vulnerabilities at the time of writing).

Live deployment hardening:

  • JWT verification instead of trust: the API validates the Cognito ID token's RS256 signature against the pool's JWKS using node:crypto (no SDK), then checks iss, aud/client_id, exp and token_use. A forged, expired, wrong-pool or non-ID token is a 401
  • Session expiry is enforced client- and server-side: the guard treats an expired token as signed out, and the API would reject it anyway
  • No SSH on the EC2 host: port 22 is not opened at all; the security group allows 8080 only from the AWS-managed CloudFront origin-facing prefix list, and administration happens through SSM Session Manager / Run Command
  • IMDSv2 required, one-hop response limit, and an encrypted gp3 root volume
  • No long-lived AWS credentials: GitHub Actions assumes a role via OIDC that is scoped to this repository, this bucket, this distribution and this instance
  • Runtime secrets stay on the host: the deployed stack's Cognito ids, CORS origin and database passwords are written into a root-only .env by the CloudFormation user data script — never in Git, never in an image, and the passwords are NoEcho parameters in the stack
  • CloudFront enforces HTTPS for viewers, and the S3 bucket is private with a bucket policy that only permits that distribution (OAC)
  • One AWS permission, one ARN: the instance role's inline policy allows cognito-idp:AdminDeleteUser on the GameHub user pool and nothing else — no CognitoPowerUser, no * resource
  • No third-party requests from the browser: fonts are self-hosted (OFL), so loading a page discloses no visitor IP to Google or to an analytics/CDN provider. This is a German data-protection requirement in practice, not a performance preference

Data protection (GDPR)

  • Data minimisation by schema: one (user_sub, game) row per player holding the best score — no play history, no email in the score table, no IP next to a score
  • Storage limitation: access logs are retained for 7 days and then deleted automatically; the retention is set on the log groups in infra/observability.yaml and the reason is written down in the notice
  • Erasure (Art. 17): DELETE /api/me removes the database rows and the Cognito identity. The order matters — rows first — because if the identity were deleted first, a failure would leave data nobody (including the user) could ever delete. A Cognito failure returns 502 with a truthful message
  • Access & portability (Art. 15, 20): the account page lists the identity and every stored row, with a one-click JSON export
  • Transparency (Art. 13): frontend/privacy.html is a bilingual inventory — item, purpose, legal basis, retention, processors (AWS, eu-central-1) and rights
  • Not stored on purpose: passwords (Cognito holds a salted hash we never see), advertising identifiers, behavioural profiles, third-party analytics

Supply chain & pipeline

  • SBOM per build: an SPDX JSON inventory (syft) is generated in CI and kept as a build artifact
  • Two vulnerability scans, two questions: Trivy over the filesystem (source and dependencies) and over the built image (what the base image adds), plus npm audit — all failing the job on CRITICAL/HIGH
  • Secret scanning over history, not just the diff: gitleaks runs against the full git history, because a secret that was committed and removed is still leaked
  • Dependabot for npm, GitHub Actions and base images: updates arrive as reviewable pull requests that must pass the same CI, with no auto-merge
  • The deploy is gated on CI, not on the push: .github/workflows/deploy.yml triggers on a successful CI run for a specific commit and checks out that commit, so a merge cannot reach production before the tests have judged it
  • Post-deploy verification against the public URL: the pipeline finishes by checking the homepage, all 12 catalogue entries through the API, game details by id, and that an unauthenticated /api/me returns 401 — the edge, not just the host
  • Branch protection on main: the four CI jobs are required status checks in strict mode, administrators are not exempt, force-pushes and branch deletion are disabled, and unresolved conversations block the merge. The gate is only a gate if the merge itself is gated

Things that had to be got right

  1. TreatMissingData is a decision, not a default. For the host metrics, missing data is notBreaching — a stopped agent should not page anyone. For the synthetic check it is breaching: no data means the checker itself is broken, and an availability monitor that fails silently is worse than none.
  2. The agent must not create the log groups. If the agent starts first, the groups exist without retention and CloudFormation's AWS::Logs::LogGroup fails with AlreadyExists on the next deploy. The template owns the groups; the agent only writes into them.
  3. A metric filter is not a log parser you can debug in place. Pattern syntax errors produce an alarm that never fires — no warning, no log entry. The check that matters is a manual canary invocation followed by get-metric-statistics, proving a data point exists, not that the template was accepted.
  4. *Metric dimensions must match exactly.* CWAgent attaches InstanceId, and the disk plugin adds path, device and fstype on top. An alarm whose dimension set is one key short sits in INSUFFICIENT_DATA forever. The dimensions in this stack were read back from list-metrics on the running host, then written into the template — verified, not guessed.
  5. The synthetic check measures the path a user takes. It calls the CloudFront URL, not localhost — otherwise it proves the host is alive while the CDN is broken, which is exactly the failure it is meant to catch.
  6. Alarms without a subscriber are half a feature. The topic is created and exported; subscribing is one aws sns subscribe because the account's own contact address cannot be read by an alarm template. Documented in docs/runbook.md §8 rather than pretended away.
  7. Latency is measured where the user waits. $request_time includes the upstream Express call; $upstream_time alone would hide the time nginx spends. Having both on the log line is what lets the runbook split "slow app" from "slow edge" with one query.
  8. A metric filter publishes its default value for every event that does not match. The canary alarm was built on Average of a metric emitted from a Lambda log group, and it sat in ALARM with an average of 0.4 while every check was passing: the group also contains START, END and REPORT lines, each of which contributed a zero. The fix is not a different threshold, it is a different statistic — one JSON line per run, summed, so the zeros add nothing. The same trap is why numeric-extraction filters ($.request_time) must only be pointed at log groups where every event matches; the nginx group qualifies because only /api/* traffic reaches the origin, and the S3-served page requests never enter it.
  9. The agent has to be root to read Docker's container logs. /var/lib/docker/containers/*/*-json.log is 0640 root:root inside a 0710 directory. Running the agent as its own cwagent user collected host metrics perfectly and shipped nothing from the containers — a silent half-failure, because the metrics half looked healthy. The log group stayed empty until run_as_user was set to root, with the reason written next to it.
  10. A policy that is only in the template does not exist on a running host. The instance role gained CloudWatchAgentServerPolicy in the template, but the live host was created before that, so the agent started and was immediately refused with AccessDeniedException: ... not authorized to perform: logs:PutLogEvents. IaC is a description of the desired state; the running instance remains the old state until it is redeployed or the change is applied. (Attaching the policy by hand made reality match the template again — the template was already correct.)

Things that had to be got right

  1. log_format is an http-level directive. The nginx config is a server block placed in conf.d/, so the structured log format had to move into its own file (frontend/nginx-log-format.conf, copied in as 00-log-format.conf) or nginx exits with "log_format" directive is not allowed here. Found by the container restarting instead of serving — the failure was loud and immediate, which is the good kind.
  2. Ports belong to a machine, not to a plan. kind's NodePort mapping wanted host 8080, which this Mac already uses (a Compose frontend and an unrelated SSH tunnel). The cluster now publishes on 8081, so Compose and Kubernetes can run at the same time — and the smoke test takes the URL as an argument.
  3. prune and selfHeal are the whole argument for GitOps. Without them, Argo CD is an expensive kubectl apply that never re-reconciles. With them, scaling a Deployment by hand is a bug that gets fixed within a minute — which is exactly what the verification demonstrates.
  4. A PVC on kind is a PV on a container filesystem. It works, it persists across pod restarts, and it dies with the cluster. That is the correct scope for a learning environment; the AWS stack keeps its data on an EBS-backed volume with a snapshot schedule, and the two are not the same promise.
  5. imagePullPolicy: Never is a deliberate local choice. It fails fast and loudly if the image was not side-loaded, instead of silently pulling a stale latest from a public registry that has nothing to do with this project.
  6. The seed ConfigMap is generated, not hand-maintained. db/init.sql stays the single source of truth, scripts/build-k8s-dbinit.sh --check runs in CI, and a change to the schema that skips the render fails the build.
  7. readOnlyRootFilesystem was left off on purpose. The nginx image writes its PID file and cache at startup and Node may use /tmp. Turning it on needs emptyDir mounts and an unprivileged nginx image — a change worth making, but only alongside the evidence that it still serves, which is why the manifests say so in a comment rather than pretending.
  8. drop: ALL is the wrong answer for the stock nginx image. The root master process legitimately needs CHOWN, DAC_OVERRIDE, SETUID, SETGID and NET_BIND_SERVICE before it hands off to the unprivileged worker. Dropping everything produced CrashLoopBackOff in both replicas and the error chown("/var/cache/nginx/client_temp", 101) failed (1: Operation not permitted) in the container log — the pod was hardened straight into a crash, which is exactly why the capability list is now written down with its justification.
  9. The Argo CD install needs --server-side. kubectl apply of the release manifest failed with The CustomResourceDefinition "applicationsets.argoproj.io" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes — client-side apply stores the previous configuration in an annotation, and this CRD's own annotations blow past the limit. Server-side apply stores nothing in the object.
  10. read plus set -e is a trap in a wait loop. read -r a b < <(cmd) returns non-zero when cmd produces no output, and under set -eu that ends the whole script — silently, on the first poll, while the Application has no status yet. The wait loop now collects the output first and parses it defensively, which is why the script prints its progress lines instead of exiting after "waiting for the first sync".

Things that had to be got right

  1. AdminDeleteUser is an admin API, and an admin API does not accept a user's token. The player's JWT proves who is asking; it cannot authorize a pool-wide operation. The backend therefore has to sign its own AWS request — which is why this step contains a SigV4 implementation, and why the test suite asserts the signature rather than trusting it.
  2. SigV4 signs almost everything except the two things you expect. The canonical request covers the method, the URI, the query string, the canonical headers, the signed headers list and the payload hash. Miss the payload hash and the signature is still "valid" to a naive check while binding nothing — the test that changes the request body and asserts the signature changes is the one that caught this class of mistake.
  3. Temporary credentials must be signed. When the credentials come from IMDS, the session token is a header that is part of the signature (x-amz-security-token). Adding it after signing produces an error that reads like a permissions problem and is not one.
  4. IMDSv2 is a two-step protocol, and that is the point. PUT for a token, then attach it to every GET. The token is what makes an SSRF from inside a container useless — which is why the host is configured for token-required metadata and why the tests run the whole dance against a local stand-in server rather than a mock.
  5. The order of deletion is the design. Data rows first, identity second. Delete the identity first and a failure leaves data that no one — including the user — can ever delete, because the user no longer exists to authenticate. The 502 message is deliberately blunt: "Your game data was deleted, but the sign-in account could not be removed." A half-finished erasure must never be reported as a completed one.
  6. A sub is pseudonymous, not anonymous. The database holds no email address, but sub is still personal data under the GDPR. That is why the privacy notice lists it, and why it is deleted along with everything else.
  7. Request logs are personal data. The nginx/CloudWatch access logs contain IP addresses, so the 7-day retention is a data-protection decision with a legal basis (legitimate interest), not just a cost setting. It is written down in the notice, in the same table as the email address.
  8. Self-hosted fonts are a German legal requirement in practice. Loading fonts.googleapis.com transmits every visitor's IP to Google; German courts have held that this needs consent. The fonts here are self-hosted OFL files in frontend/fonts/, so the page makes no third-party request at all.
  9. db/init.sql only runs on an empty data volume. That is a real property of the official MySQL image, and it means the file that documents the schema is not the file that updates a live one. Hence the migration runner — with checksums, because a migration that silently changed after being applied is worse than no migration ledger at all.
  10. A deploy is finished when the public URL says so. The verify job runs after both deploys and checks the edge (CloudFront), not the host: real homepage markup, all 12 catalogue entries from the API, game details by id, and — the security assertion — that an unauthenticated /api/me returns 401. A crashed container, a stale origin or a bad certificate fails this job.
  11. The security scans are in CI, so they are not optional. Gitleaks over the full git history (not just the diff — a secret that was committed and removed is still leaked), Trivy against the filesystem and the built image (a package can be added by the base image), npm audit, an SPDX SBOM kept as a build artifact, and Dependabot for npm, Actions and base images.
  12. Branch protection makes the gate real. The deploy is CI-gated, but CI is only a gate if the merge itself is gated. On main: the four CI jobs are required status checks with strict mode (the branch must be up to date), administrators are not exempt, force-pushes and deletion are disabled, and unresolved review conversations block the merge. A required human approval is deliberately absent — this is a one-person repository, and a rule that GitHub refuses to satisfy (you cannot approve your own pull request) is a rule that gets disabled the first time it is inconvenient.
  13. A container is one hop further from the metadata service than the host. With HttpPutResponseHopLimit: 1 — the AWS default, and what this template originally declared — the token PUT from inside the application container is never answered. Measured on the live host: the same request returns HTTP 200 from the host shell and dies with ETIMEDOUT from inside the container. The application sees fetch failed (undici's generic wrapper), the handler's catch turns it into 502, and because the connect hangs for longer than CloudFront's origin timeout, the user sees a 504 from the CDN. Three layers separate the symptom from the cause, which is exactly why the value is now 2 in the template with the reasoning next to it rather than in a runbook. The live erasure check found this on production after the code had already been merged and deployed — the strongest possible argument for the check being a script that anyone can run.

Concepts to understand cold

  • SigV4: canonical request → string to sign → derived signing key (kSecret → kDate → kRegion → kService → kSigning) → HMAC-SHA256. Why the key is derived per region and per service.
  • IMDSv2: the token PUT, the one-hour default TTL, why link-local 169.254.169.254 is reachable from the instance and nothing else, and why HttpTokens: required is a hardening control.
  • GDPR as engineering: controller vs. processor, legal basis (contract vs. legitimate interest), data minimisation, storage limitation, and the four rights that have code behind them here (access, portability, erasure, objection).
  • Least privilege: an IAM permission scoped to a resource ARN (userpool/eu-central-1_…) instead of an action wildcard.
  • Supply chain: SBOM ≠ vulnerability scan ≠ dependency update. Three different questions, three different tools, all running on every change.

How the guide becomes a PDF

learn/guide.html is a second rendering of the same documents, print-optimised rather than screen-optimised: an A4 @page rule, a cover page with the project title, a contents list, and each document starting on a fresh page with its <h1> as the section break. scripts/build-pdf.sh locates the browser (/Applications/Google Chrome.app/… on macOS, then chromium/google-chrome on Linux, overridable with CHROME_BIN) and prints that one file. Because the guide reuses the same renderer as the site, the PDF cannot drift from what the site shows.

Things that had to be got right

  1. Tables are the whole point. The step notes and the README are mostly | … | … | tables — what was built, why, and why not the alternative. A renderer without GFM table support would have produced an unreadable site, so the table parser (header, separator, alignment from :---) was written and checked first.
  2. Inline code inside emphasis. **GET /api/games/:id** must produce a <strong> wrapping a <code>, not literal asterisks. Code spans are pulled out into placeholders before escaping and put back at the end, so they can never be re-parsed as emphasis.
  3. Fonts stay self-hosted. The site and the PDF both reference fonts/press-start-2p-latin-400.woff2 and the Chakra Petch faces relatively, and the generator copies them out of frontend/fonts/ into learn/fonts/. There is no Google Fonts import anywhere — the same GDPR reasoning as Phase 2.
  4. A second run changes nothing. The generator is deterministic: the same Markdown produces the same bytes, so re-running it never shows up as a spurious diff and CI could gate on it if the docs were generated there.
  5. The success status was the bug. /learn/ answered 200 with the game hub's landing page, and the deploy's smoke test passed on it because it asserted a string (GameHub) that both pages contain. The check is now specific: it looks for readme.html, which is on the docs landing page and nowhere else. A verification step is only as strong as its most specific assertion.

Concepts to understand cold

  • A hand-written renderer vs a framework: what you actually own when you write ~200 lines of Markdown parsing, and when that trade stops being worth it
  • Escaping order: why you extract code spans, escape, then format in a single left-to-right pass (so generated HTML is never re-scanned)
  • Print CSS: @page size: A4, break-before: page, and break-inside: avoid on table rows — how a web page becomes a document that paginates
  • Static hosting with relative paths: why every asset is referenced relatively (style.css, fonts/…, gamehub-guide.pdf) so the same files work at / locally and under /learn/ on CloudFront

How /learn/ is served

The site is plain static files with relative references, so it is published under the learn/ prefix of the same S3 bucket that serves the app, and the same CloudFront distribution serves it at <distribution>/learn/ — no second bucket, no second CDN, no new origin. CloudFront already knows how to serve objects the bucket does not make public (private bucket + Origin Access Control), so the documentation inherits that.

scripts/build-frontend.sh copies learn/ into build/frontend/learn/, so the deploy's root sync (which uses --delete) publishes the docs and keeps them: the prefix is part of the artifact being synced on every build, which is why no separate prefix-scoped sync is needed and why a delete-sync of the root cannot remove the docs by accident.

Two guards keep the published site truthful:

  • A drift check in CI: the manifests job re-runs the generator and fails on any diff against the committed learn/, and asserts that every document in README.md and docs/*.md has a page. A generated artifact that is committed and never checked is a generated artifact that goes stale — and this one already had, when README.de.md and the step notes were committed without regenerating it.
  • The PDF is excluded from that comparison, because it is rendered by a headless browser and is not byte-reproducible on a runner. make learn regenerates the site and the PDF together, and the deploy publishes whatever is committed.

A directory URL is not a file

/learn/ first answered 200 with the game hub's landing page. An S3 origin reached through an Origin Access Control is a REST origin: it has no notion of an index document, so a request for the key learn/ is a 403 — and the distribution's custom error responses turn a 403 into /index.html with a 200. A wrong page wearing a success status is worse than an error, because nothing reports it; the deploy's own smoke test passed on it.

The fix is a twelve-line CloudFront Function on the viewer request of the static cache behaviour: a URI ending in / gets index.html appended, and an extensionless last segment is treated as a directory so /learn works as well as /learn/. It returns /api/* untouched, so its correctness does not depend on cache-behaviour routing. Twelve URI cases are exercised locally before the function is deployed, and the reasoning — including why a real learn/ object in the bucket was rejected — is ADR-017 in decisions.md.

ADR-001

One Compose file for local development and production

Context. The project has to run on a laptop with one command and on an EC2 host. Two definitions of "the stack" drift.

Decision. docker-compose.yml is the only definition. The host clones the repository and runs the same file, the same images and the same environment variable names.

Consequences. A bug found locally is a bug in production, and the EC2 host needs Git + Docker and nothing else. The host runs MySQL in a container, so the database is stateful inside Docker — acceptable at this size, wrong at scale.

Rejected. A separate production compose file (two files to keep in sync); ECS/Fargate (more moving parts than the app).

ADR-002

MySQL in a container, not RDS

Context. A managed database with backups and patching is what a real service would use; it is also the largest line item in a small AWS bill.

Decision. MySQL 8.4 in a container on the host, seeded from db/init.sql on an empty volume.

Consequences. Zero cost, and the schema is reproducible from the repository. No automated backups, no multi-AZ, no managed patching — and the project says so rather than implying otherwise. The migration path to RDS is a phase of its own.

Rejected. RDS (cost, and it would have hidden the one-command local story); SQLite (removes the realistic connection-pool and migration surface).

ADR-003

CloudFormation, not Terraform

Context. Infrastructure as code for five stacks: Cognito, S3+CloudFront, the EC2 host, observability and the OIDC provider. (A sixth, gamehub-dns, was added later for the custom domain's certificate — it lives in us-east-1 because that is the only region CloudFront accepts certificates from; see ADR-018.)

Decision. Plain YAML CloudFormation templates in infra/, one per stack, wired with outputs.

Consequences. No state file to store, lock or lose, and no third-party provider to trust. The templates are verbose, cross-stack references are awkward, and !If/!Sub are not a programming language.

Rejected. Terraform/OpenTofu (an extra state backend to run and secure for five small stacks); CDK (a build step and a runtime for what is mostly declarative configuration).

ADR-004

Keyless deploys with GitHub OIDC

Context. CI has to reach S3, CloudFront, EC2 (via SSM) and ECR-less hosts.

Decision. A GitHub OIDC provider plus an IAM role restricted to this repository, whose trust policy pins the repo and the deploy branch. Credentials are short-lived tokens from sts:AssumeRoleWithWebIdentity.

Consequences. Nothing to rotate, nothing to leak, and the role is the audit trail. The trust policy must be kept in step with repository renames — a rename breaks deploys until the condition string is updated.

Rejected. Long-lived IAM user access keys in GitHub secrets (a rotation problem and a leak risk); a self-hosted runner (cost, and a runner is not a credential strategy).

ADR-005

Self-hosted fonts, zero third-party requests

Context. The UI needs a game-style typeface. The obvious way is fonts.googleapis.com.

Decision. The four OFL-licensed woff2 files are committed under frontend/fonts/ and served from the same origin; the /learn site does the same.

Consequences. No visitor IP is disclosed to a third party at page load, which German courts have held needs consent, and no CDN dependency. The woff2 files (~120 KB total) live in the repository, and each font's licence is committed next to it.

Rejected. Google Fonts (a data-protection problem for a German audience); a system-font stack (loses the arcade look the project is about).

ADR-006

Metrics derived from structured nginx logs

Context. The SLOs need request rate, 5xx rate and latency percentiles. A plaintext access log can only be grepped.

Decision. nginx writes JSON (frontend/nginx-log-format.conf), the logs go to CloudWatch through the agent, and metric filters extract the numbers. The log_format lives in its own file because it is an http-level directive and the repository's nginx config is a server block.

Consequences. The metric definition is a CloudFormation pattern next to the alarm that uses it, and the log line is the source of truth. Metric filters are eventually consistent (~1 minute), a non-matching event still emits the filter's default value (so Sum is safe and Average is diluted), and percentiles can only be approximated from bucketed filters.

Rejected. An agent that parses logs into custom metrics (a second parser to maintain); application-level metrics only (loses nginx's view of status codes and timing).

ADR-007

The synthetic check is a scheduled Lambda writing a log line

Context. Availability should be judged from outside, on a schedule, and it should be visible on a dashboard.

Decision. EventBridge runs a small Lambda every 5 minutes; the Lambda requests the real site, asserts the result, and writes one JSON log line. A metric filter turns pass/fail into a metric, and the alarm is Sum < 1 with TreatMissingData: breaching — silence is a failure, not an unknown.

Consequences. No per-check charge and a single code path from the check to the alarm. The threshold semantics are unusual and are written down (docs/step-5-observability.md) precisely because Sum < 1 looks wrong at a glance.

Rejected. CloudWatch Synthetics canaries (a per-run cost and a second deployment model); external uptime services (a third party, and no path into the dashboard).

ADR-008

kind with the Compose images side-loaded

Context. Kubernetes manifests need to be exercised somewhere real.

Decision. A single-node kind cluster (k8s/kind-config.yaml), loaded with the same images the Compose stack builds (imagePullPolicy: Never), with the NodePort published on host 8081 so Compose keeps 8080.

Consequences. One image, two orchestrators — a manifest change is tested against the artifact that also runs locally. kind needs a capable container VM (4 CPU / 6 GiB Colima here), and a Never pull policy fails fast when the image was not side-loaded.

Rejected. minikube (a VM plus a driver argument per laptop); EKS (real money for a demo); a separate Kubernetes image build (two artifacts that can drift).

ADR-009

Argo CD with automated + prune + selfHeal

Context. "GitOps" is a claim about who owns cluster state.

Decision. An Argo CD Application points at k8s/ on main with syncPolicy.automated { prune: true, selfHeal: true }.

Consequences. The merge is the deploy, and a manual kubectl change is reverted by the controller — verified by scaling a Deployment by hand and watching it return to the declared replica count within 90 seconds. A mistake in k8s/ is now a cluster-wide change on merge, which is exactly why CI validates the manifests (kubeconform) and the generated seed ConfigMap before the merge happens.

Rejected. kubectl apply from a pipeline (state is whatever the last successful run left behind); Flux (equivalent here, and Argo CD's UI makes the demo legible).

ADR-010

JWT verification with node:crypto and the pool's JWKS

Context. The API must verify Cognito ID tokens: RS256 signature, iss, aud, exp, token_use, and a key id that rotates.

Decision. Fetch the JWKS, cache it, and verify the RS256 signature with node:crypto's createPublicKey/verify — no jsonwebtoken, no AWS SDK.

Consequences. The backend has no authentication dependency to audit, and the verification rules are visible in one file. The JWKS cache, key rotation and the kid-miss refetch path are code this project owns and tests (a forged token, an expired token, a wrong-pool token and a non-ID token each get a 401).

Rejected. jsonwebtoken (fine, but it hides the checks that are worth demonstrating); API Gateway's Cognito authorizer (removes the app's own authorization surface entirely).

ADR-011

One personal-best row per (sub, game), not a score history

Context. "Remember my high score" could be a row per play.

Decision. personal_bests has the primary key (user_sub, game) and updates with GREATEST(score, VALUES(score)). The player is referenced by the Cognito sub; the table holds no email address.

Consequences. The feature works with one row per player per game, so the data a breach would expose is smaller than it needed to be, and deletion (DELETE /api/me) is a single indexed delete. The cost is real: there is no history, so no leaderboard-over-time, no graphs, no "your last 10 games" — features that would require collecting personal data the app currently has no reason to hold.

Rejected. An append-only scores table (a behavioural record collected for a feature that does not exist); keying on email (copying an identifier into a second system for no benefit).

ADR-012

SigV4 by hand over IMDSv2 credentials, no AWS SDK

Context. Account deletion needs cognito-idp:AdminDeleteUser, which is an admin API: the player's JWT cannot authorize it, so the backend must sign its own AWS request.

Decision. backend/cognito.js fetches temporary credentials from the instance metadata service with IMDSv2 (a PUT for a token, the token on every GET) and signs the request with a hand-rolled SigV4 implementation.

Consequences. No SDK in the image, no long-lived keys on the host, and the signing algorithm is asserted in tests (canonical request, signed-header list, payload binding, session token included in the signature). The maintenance cost is real: the code is this project's to keep correct, and the tests are the reason that is acceptable.

Rejected. @aws-sdk/client-cognito-identity-provider (tens of megabytes and a credential-provider chain for one call); IMDSv1 (any SSRF becomes role theft); a long-lived IAM user key (a secret on disk to rotate and leak).

ADR-013

A checksummed migration runner, not only init.sql

Context. db/init.sql runs once, on an empty data volume. A live database that already has data can never be changed by editing it.

Decision. scripts/migrate.sh applies files from db/migrations/ in order, recording each in a schema_migrations ledger with a checksum, and refuses a migration whose file changed after it was applied. It reaches MySQL through docker compose exec on a host and the mysql client in CI.

Consequences. The same script is used by the deploy, by CI, and by a developer, and the ledger answers "what has been applied here?". The rule that a migration is immutable once applied is a discipline the tool only enforces for files it has seen before.

Rejected. Relying on init.sql plus manual ALTER statements on the host (undocumented, unrepeatable); a framework (a dependency for ~100 lines, and the runner is a teaching artifact here).

ADR-014

Deploy on a successful CI run, not on the push

Context. A push to main should reach production, but only after the tests have judged it — and, with concurrent merges, not a later commit than the one tested.

Decision. .github/workflows/deploy.yml triggers on workflow_run for the CI workflow completing on main with conclusion == 'success', and checks out github.event.workflow_run.head_sha.

Consequences. Production receives exactly the commit CI passed. Path filters are gone, so a documentation-only merge re-deploys identical content (idempotent, and worth the safety). The pipeline ends with a smoke test against the public CloudFront URL.

Rejected. Deploying on push (a race against CI); a single workflow with jobs depending on each other (couples a 20-minute test run to a deploy trigger).

ADR-015

No package manager in the runtime image

Context. A Trivy scan of the backend image reported 10 HIGH findings, all inside /usr/local/lib/node_modules/npm — the package manager's own bundled dependency tree, in an image whose entrypoint is node server.js.

Decision. Remove npm, npx and corepack from the runtime layer after npm ci has installed the production dependencies.

Consequences. A smaller image, fewer findings, and no package manager for an attacker to use if the process is ever compromised. The image can no longer be used for interactive dependency debugging (docker run … npm … needs a build stage or a different image), which is the intended trade.

Rejected. Accepting the findings with a .trivyignore (the vulnerable code is not needed at runtime, so removing it beats excusing it); moving to a distroless base (attractive, but it removes the shell this project uses for HEALTHCHECK and for diagnosing the container).

ADR-016

A post-deploy check must assert what production actually does

Context. The first version of the deploy's verify job fetched /api/games without a token and asserted 200 with 12 games. Against production it got 401 — the auth gate doing exactly its job — and failed the deploy. Nothing was wrong with the deployment: the check encoded an assumption that stopped being true when the catalogue moved behind the sign-in gate, and nothing re-examined the check when that happened. The identical wrong assumption appeared a second time, independently, in the load tool's success metric.

Decision. Anonymous requests are asserted to be refused (401 on every protected route), and anything needing real data signs in as a dedicated smoke identity — smoke-test@gamehub.example, credentials in the repository secrets SMOKE_USER_EMAIL / SMOKE_USER_PASSWORD — and then uses that token exactly as a browser would. The check also covers /learn/ and the PDF.

Consequences. The green tick means "a player can do what a player does": edge, JWKS verification, database and docs, not merely "something answered". It depends on one Cognito identity and two repository secrets; if they are missing the job fails loudly, which is the right failure mode for a gate. A test that cannot fail for the right reason is not a test.

Rejected. Making /api/games public again so the old assertion would pass (letting the check reshape the product); asserting only that the routes answer (a 401 and a 200 are both "answering" — the cheapest way to have a green check that proves nothing).

ADR-017

Directory URLs are rewritten at the edge, not stored as folder objects

Context. /learn/ answered 200 with the game hub's landing page. An S3 origin behind an Origin Access Control is a REST origin and has no index document: a request for the learn/ key is a 403, and the distribution's custom error responses turn a 403 into /index.html with a 200. The deploy's smoke test passed on that wrong page, because its only assertion (GameHub) is true of both pages.

Something has to resolve /learn/. Three candidates: write /learn/index.html in every link, store a real object under the key learn/, or rewrite the URI at the edge.

Decision. A CloudFront Function on the viewer request of the static cache behaviour appends index.html to a URI that ends in /, and treats an extensionless final segment as a directory so /learn works too. It returns /api/* unchanged, so the function is correct independently of which cache behaviour it is attached to. Its ten-to-twelve URI cases are exercised locally before it is published.

Consequences. /learn/, /learn and every deep link work; the bucket stays dumb; the cost is nil at this size (the CloudFront Functions free tier is two million requests a month against a few thousand here). The trade is one more piece of logic between the user and the object, so it fails open — an unmatched URI behaves exactly as it did before — and it is small enough to read in one sitting.

Rejected. Uploading the landing page also as the key learn/ (S3 permits it, but aws s3 sync --delete does not know it is meant to exist, so it would be deleted and restored on every deploy — a one-second outage per release in exchange for saving twelve lines); linking to /learn/index.html everywhere (works, and the docs' own links do use explicit .html, but /learn/ is the URL a person types or bookmarks, and a landing page that renders the wrong site is a bug however it was linked).

ADR-018

The site answers on a custom domain — and the CloudFront name keeps working

Context. The site was reachable only at d2qf9zxehny6bk.cloudfront.net. The zone worldofvpc.online already existed with another project on the apex, so gamehub.worldofvpc.online was the obvious subdomain. The expected cost was breaking the CloudFront name: the distribution redirects HTTP to HTTPS, so if a custom certificate replaced the default one, the old address would fail at the TLS handshake and any link to it would simply break.

Decision. Serve gamehub.worldofvpc.online: an ACM certificate issued in us-east-1 by a small dedicated stack (infra/dns.yaml) and validated over DNS, an alias on the distribution, and IPv4/IPv6 alias records pointing at it. Prefer the custom name wherever a URL is written down — README, docs, the load-test commands and the deploy's smoke test — and treat the CloudFront name as an implementation detail.

Consequences. The expectation was wrong in a pleasant way, and it was measured rather than assumed: CloudFront chooses the certificate by SNI, so the alias gets the certificate for gamehub.worldofvpc.online while the distribution's own name keeps getting *.cloudfront.net. Both names answer 200, so no existing link breaks and the historical verification records stay exactly as they were written. The real cost is a third stack (in us-east-1, because CloudFront only accepts certificates from there), a hosted-zone id in the site stack, and the standing obligation to rename everywhere at once — a half-renamed project is worse than an unnamed one. Certificates are free; alias records are not charged for.

Rejected. Load test — what a single t3.micro actually does ✅ (2026-10-19)

Verified by: two runs of scripts/load-test.js against the live deployment on 2026-10-19 at 09:35–09:36 UTC (4,000 requests total), with the origin-side numbers read back from the app's own request log (/gamehub/prod/app) and nginx's access log (/gamehub/prod/nginx-access) in CloudWatch, and the instance's CPU, memory and all eight alarm states read back from CloudWatch for the same window.

Why this exists, and what it is not

A load test is only useful if it is honest about what it measured. This one was built to answer a narrow question — does a two-vCPU burstable instance with a containerised MySQL comfortably serve this application? — and it deliberately does not try to find the breaking point.

Three things make the result trustworthy rather than flattering:

  1. Three vantage points, not one. The client measures end-to-end latency (which, from a home connection, is mostly the network). nginx's request_time measures what the origin spent. The backend logs its own duration_ms per request, which is the handler alone. Reporting only the first number would have said "180 ms per request" and meant almost nothing.
  2. The mix is weighted and declared. 50 % static site (/, served by CloudFront), 30 % API list (/api/games, a database read), 20 % liveness (/api/health, no database). The weights are in the script.
  3. Each endpoint declares its expected status. 401 from the gated catalogue route is the auth gate working, not an error — so the anonymous run scores 401 as expected, and a 200 there would be the finding. Without that, the first run "failed" with a 70 % success rate while the system was perfect.

What this does NOT prove

  • One client, one location. Concurrency 20 from a single machine is not distributed load; CDN edge performance for a user in another country is untested.
  • No saturation point. Neither run pushed CPU past 7 %, so the numbers say "comfortable at this level", not "this is the ceiling".
  • A burstable instance is burstable. The t3.micro earns CPU credits while idle and spends them under load. A 19-second burst is exactly what the family is designed for; a sustained load test is a different experiment, and the gamehub-prod-cpu-credit-balance-low alarm exists because of it.
  • A warm static cache. The static half of the mix was a cache hit throughout. A cold-cache storm is a CloudFront capacity question, not an instance one, and is not covered here.
  • The write path is sampled, not load-tested. Two POST /api/scores and one DELETE /api/me are enough to characterise one request, not to make a claim about write throughput.
  • No adversarial traffic. No rate limiting, no abuse pattern, no large payloads — those belong to a security review, not a capacity one.

Cost

4,000 requests from CloudFront plus ~2,000 origin-bound requests and a few hundred kilobytes of transfer. CloudFront's free tier is 1 TB and 10 million requests per month; the instance is billed whether it is busy or idle. The marginal cost of this test was effectively zero, and nothing here approaches a paid tier.

Runbook — GameHub (prod)

One section per alarm. Each one says what the alarm means, how to confirm the cause with a command, and what to do about it. Everything here is done over SSM — there is no SSH access to the host by design.

0. Ground rules

export AWS_REGION=eu-central-1
export INSTANCE_ID=$(aws ec2 describe-instances --region "$AWS_REGION" \
  --filters Name=tag:Name,Values=gamehub-prod* \
  --query "Reservations[].Instances[].InstanceId" --output text)
# The site's canonical name. The distribution's own domain name also still
# answers, with CloudFront's default certificate — see ADR-018.
export SITE_URL=https://gamehub.worldofvpc.online

Run a command on the host (no keys, no SSH — IAM decides who may do this):

aws ssm send-command --region "$AWS_REGION" --instance-ids "$INSTANCE_ID" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["docker compose -f /opt/gamehub/docker-compose.yml ps"]' \
  --query Command.CommandId --output text

Check every alarm at once:

aws cloudwatch describe-alarms --region "$AWS_REGION" \
  --alarm-name-prefix gamehub-prod \
  --query "MetricAlarms[].[AlarmName,StateValue]" --output table

The general shape of the response is always the same: state → evidence → action, and only ever through code, never the console.

2. gamehub-prod-http-5xx

Means: more than 5 responses with status >= 500 in 5 minutes behind nginx.

7. Rollback

The pipeline is the only way changes reach the host, so the rollback is also a pipeline operation:

git revert <bad-sha>          # or: git revert --mainline 1 <merge-sha>
git push origin main

deploy.yml publishes the site and rolls the host to the reverted commit. The frontend image is built on the host from the checked-out commit, so "the previous version" is exactly the previous commit — no image registry needed. Database changes are the one thing a revert does not undo: the schema is additive (see backend/schema.sql), which is why it can be.

8. Escalation and evidence

  • Alarms: gamehub-prod-alarms (SNS). Subscribe with aws sns subscribe --topic-arn <arn> --protocol email --notification-endpoint <you@example.com> and confirm the mail.
  • Dashboard: gamehub-prod (CloudWatch) — availability, error count, latency percentiles, host pressure, live log tables.
  • Logs: /gamehub/prod/nginx-access (structured JSON, every request) and /gamehub/prod/app (container stdout/stderr, JSON from Express).
  • Audit: CloudTrail records every ssm:SendCommand, so "who restarted the host at 03:00" has an answer.
  • Post-deploy check: the verify job in deploy.yml asserts the public edge: the shell, /learn/ and the PDF, the auth gate (401 without a token on every protected route), and — signing in as smoke-test@gamehub.example — a 12-entry catalogue and an identified user. Its credentials are the repository secrets SMOKE_USER_EMAIL / SMOKE_USER_PASSWORD; to rotate, run aws cognito-idp admin-set-user-password --user-pool-id "$COGNITO_USER_POOL_ID" --username smoke-test@gamehub.example --password '<new>' --permanent and update both secrets. 3. How the numbers are actually produced

browser ──▶ CloudFront ──▶ S3 (static site)
                     └───▶ EC2 nginx ──▶ Express /api/*
                              │
                              ├─ JSON access log  ──▶ CloudWatch Logs ──▶ metric filters
                              │            (status, request_time)          │
                              │                                    CloudWatch metrics
                              └─ CloudWatch agent ──▶ CWAgent            │
                                     (mem, disk, swap)                  ▼
EventBridge ──5 min──▶ Lambda ──▶ CloudWatch Logs ──▶ synthetic metrics ──▶ Alarms ──▶ SNS
  • Availability and latency come from measured traffic and a synthetic check, never from the alarm configuration.
  • Requests counts every log line, ServerErrors counts status >= 500; the error ratio is a CloudWatch metric math expression on the dashboard (ServerErrors / Requests), not a metric filter, so neither side can drift.
  • The canary emits one JSON line per run and the alarm sums it: 1 means "the run happened and both checks passed". A metric filter publishes its default value (0) for every log event that does not match — including the Lambda's own START/END/REPORT lines — so summing is the only statistic that ignores the noise instead of averaging it in.
  • Latency is the nginx $request_time, which includes the upstream Express call — the number a user actually feels, not just the time spent in Node.
  • TreatMissingData is breaching only for the two availability alarms. For the synthetic check, silence means the checker itself died, which is a page.

4. When an objective is missed

  1. The alarm fires to the gamehub-prod-alarms SNS topic (email subscription).
  2. The on-call response is written down in runbook.md — one section per alarm, with the exact commands to look at, not advice to "investigate".
  3. If the miss was caused by a deploy, the rollback is git revert on main, which re-triggers the pipeline and republishes the previous commit. The container images are pinned to commits, so the previous version is one revert away.
  4. If the miss was not caused by a deploy, the fix is a code or infra change on a branch, reviewed and merged like any other change — no hand-editing in the AWS console.

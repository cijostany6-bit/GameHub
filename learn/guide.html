🎮 GameHub

A Futuristic Gaming Platform Built with AWS & DevOps

CI License: MIT Tests Coverage

GameHub is a portfolio project that combines a futuristic gaming interface with a containerized Node.js backend and a MySQL database — all runnable locally with one command. It demonstrates how frontend applications, backend APIs, container networking, reverse proxies, databases, tests and CI pipelines work together.

The project is being evolved into a production-style application: automated CI/CD, infrastructure as code on AWS, monitoring, and Kubernetes (local kind cluster + Argo CD).

Status — Phase 4 complete (2026-10-19): tested, CI'd, game-y, playable, and live on AWS. 64 automated tests, a Cognito sign-in gate, the static site on S3 + CloudFront, the API on EC2, all described as CloudFormation and deployed by keyless GitHub OIDC.

Live demo: https://d2qf9zxehny6bk.cloudfront.net — create an account (email confirmation), sign in, and play. The landing page is public; the catalogue and the games require a signed-in player.

✅ Completed (Phase 4 — real auth + live on AWS)

  • Cognito sign-in gate: sign-up with email confirmation, sign-in, sign-out. The static frontend talks to Cognito's REST API directly (no Amplify, no SDK) and sends the ID token as a Bearer header on every /api/* call
  • Server-side token verification (backend/auth.js): RS256 signature checked against the pool's JWKS with node:crypto, plus iss, aud/client_id, exp and token_use — no jsonwebtoken dependency
  • Honest fail-open: the gate is enforced only when the pool is configured; local development runs open and the backend logs an auth_disabled warning at boot — never a silent bypass
  • Static site on S3 + CloudFront: private bucket, CloudFront Origin Access Control, /api/* behaviour with caching disabled, HTML short-cache vs assets long-cache
  • API host on EC2 running the same docker-compose.yml as local development (nginx + Express + MySQL), with a 2 GB swap file for headroom
  • No SSH: the security group opens port 8080 to the AWS-managed CloudFront origin-facing prefix list only; administration is via SSM Session Manager, IMDSv2 is required and the root volume is encrypted
  • Four CloudFormation stacks (infra/cognito.yaml, site.yaml, backend.yaml, github-oidc.yaml) — one command per stack, outputs wired into the next
  • Keyless deploys: GitHub Actions assumes a scoped role through OIDC (no AWS access keys anywhere); the workflow publishes the site, invalidates CloudFront and rolls out the API host over SSM
  • Landing page stays public while the catalogue and the runner require a signed-in player — found by actually signing out live and following the redirect, not by reading the code
  • Versioned asset URLs (script.js?v=<deploy sha>): assets are cached for a week, so a CloudFront invalidation alone still leaves returning browsers on the previous script. HTML (one-minute cache) points at the new version — found by watching a stale script.js run in the browser after a deploy

✅ Completed (Phase 5 — observability)

  • Structured request logs: nginx emits JSON access logs (status, uri, request_time, upstream_time) — CloudWatch parses them without regex guesswork
  • CloudWatch agent on the host: ships those logs plus container stdout to /gamehub/prod/nginx-access and /gamehub/prod/app (7-day retention set by the template), and host mem/disk/swap metrics into the CWAgent namespace — installed by user-data, no manual setup
  • Metrics derived from logs (AWS::Logs::MetricFilter): request count, 5xx count, and API latency as a numeric extraction ($.request_time) for p50/p99 — nginx already knew the numbers, so the app is not instrumented with an extra library to repeat them
  • External availability check: EventBridge runs a small Lambda every 5 minutes against the public CloudFront URL and /api/health; its log line becomes the SyntheticSuccess metric — a synthetic check without the CloudWatch Synthetics price tag
  • Eight alarms into one SNS topic: synthetic availability (TreatMissingData: breaching — silence is a failure), 5xx count, API p99 latency, instance status, CPU, CPU credits, memory and disk. Host-metric alarms treat missing data as notBreaching, because a stopped agent is not an outage
  • One dashboard (gamehub-prod): availability, requests vs errors, latency percentiles, host pressure, and two live log tables (recent 5xx, backend tail)
  • SLOs with error budgets (docs/slo.md): 99.5 % availability and p99 ≤ 1.5 s over a rolling 30 days, with the measurement method for each — and an explicit list of what is not claimed, because a single-AZ t3.micro cannot honestly promise it
  • Runbook (docs/runbook.md): one section per alarm with the exact SSM/Logs-Insights commands to confirm the cause, plus the revert-to-roll-back path
  • Verified live, not assumed: the agent's metric dimensions were read back from list-metrics and then written into the template — an alarm with the wrong dimension set sits in INSUFFICIENT_DATA forever

Request flow

  1. A user opens GameHub in the browser.
  2. Nginx serves the static frontend files.
  3. JavaScript sends API requests to the frontend's /api/ path.
  4. Nginx forwards those requests to the backend container.
  5. Express processes the request and queries the MySQL container over the private Docker network.
  6. The backend returns JSON, which the frontend uses to render game cards.

Important: The browser accesses the frontend through port 8080. The Nginx container communicates with the backend using Docker networking, and the backend port is not published to the host — the database runs as a local MySQL container (managed by hand, not by IaC — see the note in the Database section).

The browser signs in against Cognito, receives an ID token, and sends it as Authorization: Bearer <token> on every API call. The backend verifies the token's RS256 signature against the pool's public JWKS — the frontend guard is UX, the API is the security boundary.

🚀 Run GameHub Locally

Prerequisites

  • macOS or Linux
  • Git
  • A Docker runtime + Docker Compose (on this Mac: Colima — start it with colima start)

No configuration needed. The stack ships with working local defaults: a MySQL container is seeded automatically from db/init.sql on first start.

1. Clone and bootstrap

git clone https://github.com/cijostany6-bit/GameHub.git
cd GameHub
make bootstrap        # build → start → wait for health → run smoke tests

2. Open GameHub

http://localhost:8080

Useful commands

make ps               # container status (healthy?)
make logs             # tail all logs
make smoke            # re-run the end-to-end checks
make test             # backend unit + integration tests (needs MySQL)
make test-frontend    # game-engine, mapping-contract and auth tests (Node only)
make down             # stop, keep database data
make db-reset         # wipe + re-seed the database
make clean            # full teardown incl. images and DB volume
make help             # list all targets

Prefer plain Compose? docker-compose up -d --build then ./scripts/smoke.sh does the same.

☁️ Deploy to AWS

Everything is CloudFormation in infra/ — five small stacks, each one a single command. Stack outputs feed the next stack, so there is no spreadsheet of ids to copy by hand.

export AWS_REGION=eu-central-1

# 1. Cognito user pool + app client
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-cognito --template-file infra/cognito.yaml \
  --parameter-overrides Stage=prod

# 2. S3 + CloudFront (deployed first without an API origin)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-site --template-file infra/site.yaml \
  --parameter-overrides Stage=prod

# 3. EC2 host running the compose stack (needs the CloudFront domain)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-backend --template-file infra/backend.yaml \
  --parameter-overrides \
    Stage=prod \
    CognitoUserPoolId=<pool id> \
    CognitoClientId=<client id> \
    SiteOrigin=<https://cloudfront domain> \
    DbPassword=<16+ chars> RootDbPassword=<16+ chars>

# 4. Re-deploy the site stack with the API origin attached, then publish
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-site --template-file infra/site.yaml \
  --parameter-overrides Stage=prod BackendOriginDomain=<ec2 public dns>

AWS_REGION=$AWS_REGION ./scripts/deploy-frontend.sh

# 5. Observability: log groups + retention, metrics from logs, the synthetic
#    check, eight alarms and the dashboard. AlarmEmail is optional — without it
#    the SNS topic is still created and can be subscribed later (see the
#    TopicArn output), it just has no subscriber yet.
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-observability --template-file infra/observability.yaml \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    Stage=prod \
    InstanceId=<ec2 instance id> \
    SiteUrl=<https://cloudfront domain> \
    AlarmEmail=<you@example.com>

Deploy the observability stack before the host's CloudWatch agent writes its first log line: the template owns the log groups so their retention is set, and an agent-created group would make that resource fail with AlreadyExists.

For continuous deployment, deploy the fourth stack (infra/github-oidc.yaml) once, then set these GitHub repository variables and push to main — the deploy workflow does the rest through OIDC, with no AWS keys stored anywhere:

AWS_REGION, AWS_DEPLOY_ROLE_ARN, SITE_BUCKET, DISTRIBUTION_ID, INSTANCE_ID, COGNITO_USER_POOL_ID, COGNITO_CLIENT_ID.

Cost note (honest): the site (S3 + CloudFront), Cognito and the four CloudFormation stacks are inside the free tier at this traffic level. The EC2 instance is the only line item: this account is on a free plan, so AWS rejects instance types that are not free-tier eligible (t2.micro failed with "not eligible for Free Tier") — the stack therefore defaults to t3.micro. On a non-free-tier account that is roughly $8/month. Tear everything down with aws cloudformation delete-stack in reverse order.

🔌 Backend API

The following endpoints are implemented in the current application.

MethodEndpointPurpose
GET/api/healthLiveness — process is up (never touches the database)
GET/api/readyReadiness — database reachable, safe to route traffic (503 otherwise)
GET/api/gamesRetrieve games from the database
GET/api/games/:idSingle game (powers the runner); 404 for unknown and non-numeric ids
GET/api/meEchoes the verified Cognito identity — proof the token was checked

The API is reachable only through the nginx proxy on :8080 — port 3000 is deliberately not published to the host (use docker-compose exec backend … if you need direct access from inside the network).

Auth behaviour: middleware on every /api/* route except the two probes. If the Cognito pool is configured (that is: in the deployment), requests without a valid ID token get 401 {"error":"Unauthorized"}. If it is not configured (local development), requests pass through and the backend logs auth_disabled at boot — so the app is never broken, but the bypass is never silent either.

curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl http://localhost:8080/api/games
curl http://localhost:8080/api/games/4

# with the pool configured, protected routes need the ID token:
curl -H "Authorization: Bearer $ID_TOKEN" http://localhost:8080/api/me

Or run the full check suite: make smoke.

🗄️ Database

GameHub uses MySQL 8.4 in a container, seeded automatically from db/init.sql on the first start of an empty volume. This makes a fresh clone reproducible with no cloud account and no secrets — and the deployed stack runs the same container on the EC2 host, so there is exactly one database setup to reason about. Moving to RDS (multi-AZ, automated backups, managed patching) is a deliberate cost/ops trade-off left for a later phase rather than a claim made here.

Reset to a clean seeded state any time with make db-reset.

The current games table contains these fields:

ColumnPurpose
idGame identifier
nameGame title
categoryCategory used by the frontend filters
descriptionShort game description

Sample categories include Action, Racing, and Strategy.

The frontend retrieves game records dynamically through the Express API rather than relying entirely on hardcoded game cards.

🔐 Security Practices

  • No secrets required for local development — compose defaults live in the private Docker network; nothing sensitive exists in the repo.
  • .env is excluded from Git and from image builds (backend/.dockerignore); backend/.env.example documents every variable.
  • The backend runs as a non-root user and reads all configuration from environment variables (12-factor).
  • The API port is not published to the host — only nginx on :8080 is reachable.
  • npm ci from a committed lockfile; the dependency tree is audited (0 vulnerabilities at the time of writing).

Live deployment hardening:

  • JWT verification instead of trust: the API validates the Cognito ID token's RS256 signature against the pool's JWKS using node:crypto (no SDK), then checks iss, aud/client_id, exp and token_use. A forged, expired, wrong-pool or non-ID token is a 401
  • Session expiry is enforced client- and server-side: the guard treats an expired token as signed out, and the API would reject it anyway
  • No SSH on the EC2 host: port 22 is not opened at all; the security group allows 8080 only from the AWS-managed CloudFront origin-facing prefix list, and administration happens through SSM Session Manager / Run Command
  • IMDSv2 required, one-hop response limit, and an encrypted gp3 root volume
  • No long-lived AWS credentials: GitHub Actions assumes a role via OIDC that is scoped to this repository, this bucket, this distribution and this instance
  • Runtime secrets stay on the host: the deployed stack's Cognito ids, CORS origin and database passwords are written into a root-only .env by the CloudFormation user data script — never in Git, never in an image, and the passwords are NoEcho parameters in the stack
  • CloudFront enforces HTTPS for viewers, and the S3 bucket is private with a bucket policy that only permits that distribution (OAC)

Design decisions

  • No supertest/jest: node:test + built-in fetch covers everything here — fewer dependencies is itself a supply-chain decision (npm audit stays 0).

The bugs we hit

Things that had to be got right

  1. AutoVerifiedAttributes + email-only username. New pools make MFA mandatory unless you opt out, and users sign in with an email address rather than a username. Both are explicit in the template.
  2. Cognito emits client_id on access tokens and aud on ID tokens. The verifier accepts either, then rejects non-ID tokens outright — accepting an access token here would hand out a weaker identity contract.
  3. The probes must never 401. /api/health and /api/ready are exempt from the gate; an orchestrator that cannot reach its own health endpoint kills a healthy service.
  4. CloudFront needs a domain name, not an IP, for a custom origin. The backend stack outputs the instance's public DNS name while the elastic IP keeps it stable.
  5. A 1 GB instance running MySQL wants swap. The user-data script creates a 2 GB swap file before starting the stack — cheap insurance against the OOM killer during a docker compose build.
  6. The artifact carries its config, the repo does not. config.js ships with authEnabled:false for local development; scripts/build-frontend.sh writes the real pool ids into a git-ignored build/ directory at deploy time.
  7. An edge invalidation is not a browser invalidation. After a deploy the browser still ran the previous script.js from its week-long cache, which made a fixed landing page look broken. The build now stamps every asset URL with the deploy version (script.js?v=<sha>) while HTML stays on a one-minute cache — the standard two-tier answer to "how do users get the new version without a hard refresh?"

Concepts to understand cold

  • OIDC federation: how a GitHub-issued JWT becomes temporary AWS credentials, and why the sub condition is what stops any other repository from assuming your deploy role
  • JWKS and key rotation: why the verifier fetches public keys instead of a shared secret, and why the result is cached
  • Edge vs origin caching: why static assets get a week and HTML gets a minute, and why /api/* must not be cached at all
  • Origin Access Control: keeping an S3 bucket private while still serving it through a CDN
  • Blast-radius reduction: no SSH, SSM-only admin, prefix-list ingress, IMDSv2

  2. "How do your CI pipelines authenticate to AWS, and what happens if the repo is compromised?" (no keys; role scoped to repo, bucket, distribution, instance)
  3. "Why is the S3 bucket private, and how does the CDN still read it?" (OAC + bucket policy condition on the distribution ARN)

Things that had to be got right

  1. TreatMissingData is a decision, not a default. For the host metrics, missing data is notBreaching — a stopped agent should not page anyone. For the synthetic check it is breaching: no data means the checker itself is broken, and an availability monitor that fails silently is worse than none.
  2. The agent must not create the log groups. If the agent starts first, the groups exist without retention and CloudFormation's AWS::Logs::LogGroup fails with AlreadyExists on the next deploy. The template owns the groups; the agent only writes into them.
  3. A metric filter is not a log parser you can debug in place. Pattern syntax errors produce an alarm that never fires — no warning, no log entry. The check that matters is a manual canary invocation followed by get-metric-statistics, proving a data point exists, not that the template was accepted.
  4. *Metric dimensions must match exactly.* CWAgent attaches InstanceId, and the disk plugin adds path, device and fstype on top. An alarm whose dimension set is one key short sits in INSUFFICIENT_DATA forever. The dimensions in this stack were read back from list-metrics on the running host, then written into the template — verified, not guessed.
  5. The synthetic check measures the path a user takes. It calls the CloudFront URL, not localhost — otherwise it proves the host is alive while the CDN is broken, which is exactly the failure it is meant to catch.
  6. Alarms without a subscriber are half a feature. The topic is created and exported; subscribing is one aws sns subscribe because the account's own contact address cannot be read by an alarm template. Documented in docs/runbook.md §8 rather than pretended away.
  7. Latency is measured where the user waits. $request_time includes the upstream Express call; $upstream_time alone would hide the time nginx spends. Having both on the log line is what lets the runbook split "slow app" from "slow edge" with one query.

Concepts to understand cold

  • The four golden signals — latency, traffic, errors, saturation — and why this dashboard is organised as exactly those four plus availability
  • Metric filters and JSON patterns — how a log line becomes a time series, including extracting a numeric value from a field ($.request_time)
  • Extended statistics — why the p99 alarm exists next to the average, and why an average latency is the metric that hides the outage
  • Error budgets — the shift from "uptime is good" to "the budget decides what we work on next", and what burning 3 h 39 m of a 30-day window means
  • Pull vs push monitoring — why the synthetic check lives outside the system it watches, in a different service, in a different failure domain
  • Retention and cost of observability — log ingestion is the subscription trap of cloud monitoring; retention is an architectural choice

  2. "Walk me through an incident: the p99 latency alarm fired. What do you do?" (runbook §3: split request_time vs upstream_time, then CPU credits, then MySQL swap)

How the guide becomes a PDF

learn/guide.html is a second rendering of the same documents, print-optimised rather than screen-optimised: an A4 @page rule, a cover page with the project title, a contents list, and each document starting on a fresh page with its <h1> as the section break. scripts/build-pdf.sh locates the browser (/Applications/Google Chrome.app/… on macOS, then chromium/google-chrome on Linux, overridable with CHROME_BIN) and prints that one file. Because the guide reuses the same renderer as the site, the PDF cannot drift from what the site shows.

Things that had to be got right

  1. Tables are the whole point. The step notes and the README are mostly | … | … | tables — what was built, why, and why not the alternative. A renderer without GFM table support would have produced an unreadable site, so the table parser (header, separator, alignment from :---) was written and checked first.
  2. Inline code inside emphasis. **GET /api/games/:id** must produce a <strong> wrapping a <code>, not literal asterisks. Code spans are pulled out into placeholders before escaping and put back at the end, so they can never be re-parsed as emphasis.
  3. Fonts stay self-hosted. The site and the PDF both reference fonts/press-start-2p-latin-400.woff2 and the Chakra Petch faces relatively, and the generator copies them out of frontend/fonts/ into learn/fonts/. There is no Google Fonts import anywhere — the same GDPR reasoning as Phase 2.
  4. A second run changes nothing. The generator is deterministic: the same Markdown produces the same bytes, so re-running it never shows up as a spurious diff and CI could gate on it if the docs were generated there.

Concepts to understand cold

  • A hand-written renderer vs a framework: what you actually own when you write ~200 lines of Markdown parsing, and when that trade stops being worth it
  • Escaping order: why you extract code spans, escape, then format in a single left-to-right pass (so generated HTML is never re-scanned)
  • Print CSS: @page size: A4, break-before: page, and break-inside: avoid on table rows — how a web page becomes a document that paginates
  • Static hosting with relative paths: why every asset is referenced relatively (style.css, fonts/…, gamehub-guide.pdf) so the same files work at / locally and under /learn/ on CloudFront

How /learn/ is served

The site is plain static files with relative references, so it can be published under the learn/ prefix of the same S3 bucket that serves the app, and the same CloudFront distribution serves it at <distribution>/learn/ — no second bucket, no second CDN, no new origin. CloudFront already knows how to serve objects the bucket does not make public (private bucket + Origin Access Control), so the documentation inherits that.

One honest caveat: scripts/deploy-frontend.sh publishes the app to the bucket root with --delete (and a versioned-asset cache split). A learn/ tree is therefore a separate, prefix-scoped sync rather than something that script does today — a delete-sync of the root would remove it. The generator emits everything the publish step needs; wiring that sync (and a /learn/ CloudFront behaviour, if it needs different caching) is the remaining deploy-side job.

Runbook — GameHub (prod)

One section per alarm. Each one says what the alarm means, how to confirm the cause with a command, and what to do about it. Everything here is done over SSM — there is no SSH access to the host by design.

0. Ground rules

export AWS_REGION=eu-central-1
export INSTANCE_ID=$(aws ec2 describe-instances --region "$AWS_REGION" \
  --filters Name=tag:Name,Values=gamehub-prod* \
  --query "Reservations[].Instances[].InstanceId" --output text)

Run a command on the host (no keys, no SSH — IAM decides who may do this):

aws ssm send-command --region "$AWS_REGION" --instance-ids "$INSTANCE_ID" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["docker compose -f /opt/gamehub/docker-compose.yml ps"]' \
  --query Command.CommandId --output text

Check every alarm at once:

aws cloudwatch describe-alarms --region "$AWS_REGION" \
  --alarm-name-prefix gamehub-prod \
  --query "MetricAlarms[].[AlarmName,StateValue]" --output table

The general shape of the response is always the same: state → evidence → action, and only ever through code, never the console.

1. gamehub-prod-synthetic-check-failed

Means: the external check could not get a 200 from the site or from /api/health within 10 seconds. This is the closest thing to "users cannot use the site".

Confirm:

curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' https://<distribution>/ 
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' https://<distribution>/api/health
aws lambda invoke --region "$AWS_REGION" \
  --function-name gamehub-prod-canary --log-type Tail /dev/stdout | tail -5

Act:

EvidenceLikely causeAction
/ fails, /api/health fineCloudFront/S3 pathcheck the distribution status, then re-run the deploy workflow (workflow_dispatch)
both failthe EC2 host is downgo to section 4 (instance status)
/api/health fails, / finethe Express container is unhealthysection 3, then docker compose up -d on the host

2. gamehub-prod-http-5xx

Means: more than 5 responses with status >= 500 in 5 minutes behind nginx.

Confirm — the log line is JSON, so this is a query rather than a grep:

# CloudWatch Logs Insights, /gamehub/prod/nginx-access
fields ts, uri, status, request_time, remote_addr
| filter status >= 500
| sort ts desc
| limit 20

Then, on the host:

docker compose -f /opt/gamehub/docker-compose.yml logs --tail=200 backend

Act: a 5xx caused by the last deploy → git revert on main and let the pipeline republish. A 5xx from the database (ER_... in the log) → check docker compose ps db and the MySQL healthcheck; the app returns 503, not a crash, so the frontend stays up.

3. gamehub-prod-api-latency-p99

Means: p99 of /api/* above 1.5 s for 10 minutes.

Confirm:

# CloudWatch Logs Insights
fields ts, uri, request_time, upstream_time
| filter uri like /^\/api/
| stats pct(request_time, 99) as p99, avg(request_time) as avg, count(*) as n by uri
| sort p99 desc

The gap between request_time and upstream_time tells you who is slow: nginx/TLS-side or Express.

Act:

CauseAction
One expensive endpointfix the query or add an index — the catalogue read and the scores read are the only DB paths
CPU saturation (see cpu-high)the instance is the bottleneck: stop a concurrent docker compose build and confirm the credit balance is recovering
MySQL swappingmemory alarm follows; the host has 2 GB swap and 1 GB RAM, so a heavy query can push MySQL into swap

4. gamehub-prod-instance-status-check-failed

Means: the hypervisor cannot reach the instance, or the OS is not responding. Everything else is noise until this is clear.

Confirm:

aws ec2 describe-instance-status --region "$AWS_REGION" \
  --instance-ids "$INSTANCE_ID" --include-all-instances \
  --query "InstanceStatuses[].[InstanceStatus.Status,SystemStatus.Status]"
aws ec2 get-console-output --region "$AWS_REGION" \
  --instance-id "$INSTANCE_ID" --output text | tail -30

Act: a system status failure is AWS-side — stop and start the instance (the elastic IP keeps the address stable) and let the user-data boot the stack again. An instance status failure with an OOM message in the console output means the stack ran out of memory: the container restart policies bring it back, but the fix is a real one (see cpu-credit-balance-low).

5. gamehub-prod-cpu-high / cpu-credit-balance-low

Means: the burstable instance is out of headroom. CPUUtilization above 85 % for 15 minutes, or fewer than 20 CPU credits left.

Confirm:

aws cloudwatch get-metric-statistics --region "$AWS_REGION" \
  --namespace AWS/EC2 --metric-name CPUCreditBalance \
  --dimensions Name=InstanceId,Value="$INSTANCE_ID" \
  --start-time "$(date -u -v-1H +%FT%TZ)" --end-time "$(date -u +%FT%TZ)" \
  --period 300 --statistics Average

# who is eating the CPU
aws ssm send-command --region "$AWS_REGION" --instance-ids "$INSTANCE_ID" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["docker stats --no-stream","uptime"]' \
  --query Command.CommandId --output text

Act: if a build is running, wait — a docker compose build on 2 vCPU is the expected cause. If it is sustained traffic, that is the signal to move the workload off the burstable class (see the roadmap), not to silence the alarm.

6. gamehub-prod-memory-high / gamehub-prod-disk-high

Means: memory above 90 % (a 1 GB instance running MySQL, Node and nginx) or the root filesystem above 85 % (Docker images and logs live there).

Confirm:

aws ssm send-command --region "$AWS_REGION" --instance-ids "$INSTANCE_ID" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["free -m","df -h /","du -sh /var/lib/docker /var/log/gamehub"]' \
  --query Command.CommandId --output text

Act:

CauseAction
Memorythe swap file in the user-data is the buffer, not the fix: reduce innodb_buffer_pool_size in db/my.cnf or move the database off the box
Disk from Dockerdocker system prune -af --volumes removes old layers (it will NOT touch the named volumes — verify with docker volume ls first)
Disk from logsthe agent ships logs with 7-day retention in CloudWatch; the local copies are rotated by Docker's json-file driver, so a runaway log is a code smell

7. Rollback

The pipeline is the only way changes reach the host, so the rollback is also a pipeline operation:

git revert <bad-sha>          # or: git revert --mainline 1 <merge-sha>
git push origin main

deploy.yml publishes the site and rolls the host to the reverted commit. The frontend image is built on the host from the checked-out commit, so "the previous version" is exactly the previous commit — no image registry needed. Database changes are the one thing a revert does not undo: the schema is additive (see backend/schema.sql), which is why it can be.

8. Escalation and evidence

  • Alarms: gamehub-prod-alarms (SNS). Subscribe with aws sns subscribe --topic-arn <arn> --protocol email --notification-endpoint <you@example.com> and confirm the mail.
  • Dashboard: gamehub-prod (CloudWatch) — availability, error count, latency percentiles, host pressure, live log tables.
  • Logs: /gamehub/prod/nginx-access (structured JSON, every request) and /gamehub/prod/app (container stdout/stderr, JSON from Express).
  • Audit: CloudTrail records every ssm:SendCommand, so "who restarted the host at 03:00" has an answer.

Service level objectives — GameHub

These are the numbers the project holds itself to, how each one is measured, and what happens when one is missed. They are deliberately modest: this is a single t3.micro instance in one availability zone, and an SLO that claims more than the architecture can deliver is a lie in a markdown file.

1. Objectives

#ObjectiveTarget (rolling 30 days)Measured byAlarm
SLO-1Availability — the public site answers 200≥ 99.5 %Synthetic check every 5 min from the Lambda canary (SyntheticSuccess)gamehub-prod-synthetic-check-failed
SLO-2API availability — /api/* answers without a 5xx≥ 99.5 %nginx access log → metric filter (ServerErrors vs Requests)gamehub-prod-http-5xx
SLO-3API latency — p99 of /api/* request time≤ 1.5 snginx access log request_time → metric filter (ApiRequestTimeSeconds)gamehub-prod-api-latency-p99
SLO-4Host health — instance status checks passno failing check for 2 minEC2 StatusCheckFailedgamehub-prod-instance-status-check-failed
SLO-5Host capacity — CPU, memory and disk stay off the ceilingCPU < 85 % · memory < 90 % · disk < 85 %EC2 metrics + CloudWatch agent (CWAgent)gamehub-prod-cpu-high, gamehub-prod-memory-high, gamehub-prod-disk-high, gamehub-prod-cpu-credit-balance-low

Two things are intentionally not SLOs:

  • Game frame rate and client-side errors — browser-only metrics, not observable from the server, so claiming a number for them would be theatre.
  • Write durability of scores — the MySQL volume lives on the instance's EBS root volume. A single-instance topology cannot honestly promise more than "the snapshot schedule in infra/backend.yaml".

2. Error budgets

ObjectiveBudget per 30 daysWhat "burning" it means
SLO-1 / SLO-2 availability ≥ 99.5 %3 h 39 m of degraded serviceOne failed 5-minute synthetic check costs 0.03 % of the budget — 36 consecutive failures exhaust it
SLO-3 latency p99 ≤ 1.5 s3 h 39 m of p99 above targetThe alarm needs 2 consecutive 5-minute windows, so a single slow render is not a page

The budget is not a dashboard number to admire; it decides priority. While the budget is intact, new features ship. Once an alarm page is unexplained, the availability work comes first — which for this project means the next roadmap item is postponed, not parallelised.

3. How the numbers are actually produced

browser ──▶ CloudFront ──▶ S3 (static site)
                     └───▶ EC2 nginx ──▶ Express /api/*
                              │
                              ├─ JSON access log  ──▶ CloudWatch Logs ──▶ metric filters
                              │            (status, request_time)          │
                              │                                    CloudWatch metrics
                              └─ CloudWatch agent ──▶ CWAgent            │
                                     (mem, disk, swap)                  ▼
EventBridge ──5 min──▶ Lambda ──▶ CloudWatch Logs ──▶ synthetic metrics ──▶ Alarms ──▶ SNS
  • Availability and latency come from measured traffic and a synthetic check, never from the alarm configuration.
  • Requests counts every log line, ServerErrors counts status >= 500; the error ratio is a CloudWatch metric math expression on the dashboard (ServerErrors / Requests), not a metric filter, so neither side can drift.
  • Latency is the nginx $request_time, which includes the upstream Express call — the number a user actually feels, not just the time spent in Node.
  • TreatMissingData is breaching only for the two availability alarms. For the synthetic check, silence means the checker itself died, which is a page.

4. When an objective is missed

  1. The alarm fires to the gamehub-prod-alarms SNS topic (email subscription).
  2. The on-call response is written down in runbook.md — one section per alarm, with the exact commands to look at, not advice to "investigate".
  3. If the miss was caused by a deploy, the rollback is git revert on main, which re-triggers the pipeline and republishes the previous commit. The container images are pinned to commits, so the previous version is one revert away.
  4. If the miss was not caused by a deploy, the fix is a code or infra change on a branch, reviewed and merged like any other change — no hand-editing in the AWS console.

OVERVIEW README.md

🎮 GameHub

🇬🇧 English version | 🇩🇪 Deutsche Version

A Futuristic Gaming Platform Built with AWS & DevOps

CI License: MIT Tests Coverage

GameHub is a portfolio project that combines a futuristic gaming interface with a containerized Node.js backend and a MySQL database — all runnable locally with one command. It demonstrates how frontend applications, backend APIs, container networking, reverse proxies, databases, tests and CI pipelines work together.

The project is being evolved into a production-style application: automated CI/CD, infrastructure as code on AWS, monitoring, and Kubernetes (local kind cluster + Argo CD).

Status — Phase 7 complete (2026-10-19): tested, CI'd, game-y, playable, live on AWS, observable, runnable on Kubernetes — and now hardened. 84 automated tests, a Cognito sign-in gate with working account deletion (GDPR art. 17, in the app rather than in a policy document), a bilingual privacy notice, an SBOM + image scanning in CI, and deploys that only run on a green CI for the exact commit. All described as CloudFormation and deployed by keyless GitHub OIDC.

Live demo: https://d2qf9zxehny6bk.cloudfront.net — create an account (email confirmation), sign in, and play. The landing page is public; the catalogue and the games require a signed-in player.

Documentation: the step-by-step write-up, the ADRs and the runbook are published as a small static site at https://d2qf9zxehny6bk.cloudfront.net/learn/, with the whole guide as a printable PDF, and every claim in it traceable to a commit and a CI run.

  • Runner state machine: READY → PLAYING → GAME OVER with Play again, HUD (score / best / status), per-title high scores in localStorage (guarded), controls help, Escape → catalogue

  • An engine test found and fixed a real stall bug (dead-centre breakout hit → vertical ball → unwinnable game)

✅ Completed (Phase 4 — real auth + live on AWS)

  • Cognito sign-in gate: sign-up with email confirmation, sign-in, sign-out. The static frontend talks to Cognito's REST API directly (no Amplify, no SDK) and sends the ID token as a Bearer header on every /api/* call
  • Server-side token verification (backend/auth.js): RS256 signature checked against the pool's JWKS with node:crypto, plus iss, aud/client_id, exp and token_use — no jsonwebtoken dependency
  • Honest fail-open: the gate is enforced only when the pool is configured; local development runs open and the backend logs an auth_disabled warning at boot — never a silent bypass
  • Static site on S3 + CloudFront: private bucket, CloudFront Origin Access Control, /api/* behaviour with caching disabled, HTML short-cache vs assets long-cache
  • API host on EC2 running the same docker-compose.yml as local development (nginx + Express + MySQL), with a 2 GB swap file for headroom
  • No SSH: the security group opens port 8080 to the AWS-managed CloudFront origin-facing prefix list only; administration is via SSM Session Manager, IMDSv2 is required and the root volume is encrypted
  • Four CloudFormation stacks (infra/cognito.yaml, site.yaml, backend.yaml, github-oidc.yaml) — one command per stack, outputs wired into the next
  • Keyless deploys: GitHub Actions assumes a scoped role through OIDC (no AWS access keys anywhere); the workflow publishes the site, invalidates CloudFront and rolls out the API host over SSM
  • Landing page stays public while the catalogue and the runner require a signed-in player — found by actually signing out live and following the redirect, not by reading the code
  • Versioned asset URLs (script.js?v=<deploy sha>): assets are cached for a week, so a CloudFront invalidation alone still leaves returning browsers on the previous script. HTML (one-minute cache) points at the new version — found by watching a stale script.js run in the browser after a deploy

✅ Completed (Phase 5 — observability)

  • Structured request logs: nginx emits JSON access logs (status, uri, request_time, upstream_time) — CloudWatch parses them without regex guesswork
  • CloudWatch agent on the host: ships those logs plus container stdout to /gamehub/prod/nginx-access and /gamehub/prod/app (7-day retention set by the template), and host mem/disk/swap metrics into the CWAgent namespace — installed by user-data, no manual setup
  • Metrics derived from logs (AWS::Logs::MetricFilter): request count, 5xx count, and API latency as a numeric extraction ($.request_time) for p50/p99 — nginx already knew the numbers, so the app is not instrumented with an extra library to repeat them
  • External availability check: EventBridge runs a small Lambda every 5 minutes against the public CloudFront URL and /api/health; its log line becomes the SyntheticSuccess metric — a synthetic check without the CloudWatch Synthetics price tag
  • Eight alarms into one SNS topic: synthetic availability (TreatMissingData: breaching — silence is a failure), 5xx count, API p99 latency, instance status, CPU, CPU credits, memory and disk. Host-metric alarms treat missing data as notBreaching, because a stopped agent is not an outage
  • One dashboard (gamehub-prod): availability, requests vs errors, latency percentiles, host pressure, and two live log tables (recent 5xx, backend tail)
  • SLOs with error budgets (docs/slo.md): 99.5 % availability and p99 ≤ 1.5 s over a rolling 30 days, with the measurement method for each — and an explicit list of what is not claimed, because a single-AZ t3.micro cannot honestly promise it
  • Runbook (docs/runbook.md): one section per alarm with the exact SSM/Logs-Insights commands to confirm the cause, plus the revert-to-roll-back path
  • Verified live, not assumed: the agent's metric dimensions were read back from list-metrics and then written into the template — an alarm with the wrong dimension set sits in INSUFFICIENT_DATA forever

✅ Completed (Phase 6 — local Kubernetes + Argo CD GitOps)

  • Real cluster, no bill: a single-node kind cluster (k8s/kind-config.yaml) with the same images the Compose stack builds, side-loaded into the node (make kind-up)
  • Deployments and a StatefulSet: frontend and backend run 2 replicas each with maxUnavailable: 0 rollouts; MySQL is a StatefulSet with a volume claim template — a Deployment would give the database a random name and two pods fighting over one data directory
  • Probes with consequences: liveness on /api/health (no database), readiness on /api/ready (database) — a DB outage stops new traffic instead of restarting every pod
  • One source of truth for the seed: db/init.sql is rendered into a ConfigMap by scripts/build-k8s-dbinit.sh, and CI fails if the copy drifts from the source
  • Least privilege, measured rather than assumed: the backend runs as the unprivileged node user with drop: ALL; nginx keeps exactly the five capabilities its root master process needs — the first attempt at drop: ALL produced CrashLoopBackOff with chown(...) failed (1: Operation not permitted), which is why the list is now written down with a reason
  • GitOps with Argo CD (k8s/argocd/application.yaml): automated sync with prune and selfHeal, so the merge to main is the deploy and a manual kubectl edit is reverted by the controller
  • Verified like the rest of the project: the same scripts/smoke.sh runs against the cluster's NodePort (8081, so Compose on 8080 keeps working) and passes — 12 games served from the StatefulSet through the nginx proxy
  • CI covers it: a manifests job validates every manifest against the Kubernetes schema (kubeconform) and checks the generated ConfigMap for drift

✅ Completed (Phase 7 — security hardening & GDPR)

  • Erasure that is implemented, not promised: DELETE /api/me deletes the player's rows and their Cognito identity in one action from the account page. A partial result is reported as a partial result (502), never as success
  • The account page is the GDPR surface: it is the access/portability answer (identity + every stored row, copyable as JSON) and it carries the deletion control — one page, three of the four rights, no support email
  • A bilingual privacy notice (frontend/privacy.html): a data inventory with purpose, legal basis and retention per item — including the 7-day access logs, which are personal data too
  • One AWS call, signed by hand: account deletion needs cognito-idp:AdminDeleteUser, so the backend fetches IMDSv2 credentials and signs the request itself (SigV4, node:crypto) — no AWS SDK, no long-lived keys, and the signature is asserted field by field in the test suite
  • Least privilege on the identity: the instance role's inline policy allows that one action on one user-pool ARN, not CognitoPowerUser on *
  • Data minimisation in the schema: one personal_bests row per (player, game) with GREATEST() on conflict — the best score, no play history — keyed by the Cognito sub, so the database holds no email address
  • Migrations with a ledger (scripts/migrate.sh, db/migrations/): db/init.sql only runs on an empty volume, so schema changes ship as checksummed, idempotent migrations; a rewritten migration is refused
  • Supply chain in CI: SPDX SBOM (syft) kept as an artifact, Trivy against the built image as well as the filesystem, npm audit, gitleaks over the full history, and Dependabot for npm, Actions and base images
  • Deploys are CI-gated: the deploy workflow runs on a successful CI run for the exact commit (never a later, untested tip of main) and finishes with a post-deploy smoke test against the public URL — homepage markup, all 12 catalogue entries, game details, and a 401 from an unauthenticated /api/me

✅ Completed (Phase 8 — /learn documentation site, PDF, load test)

  • A documentation site generated from the repository: scripts/build-learn.js (dependency-free, Node built-ins only) renders README.md and every docs/*.md into learn/ — a landing page, one page per document, a print guide, and a hand-written Markdown renderer with GitHub-style table support
  • Published with the app: build-frontend.sh copies learn/ into the deployable artifact, so the same CloudFront distribution serves the guide at /learn/ — no second bucket, no second CDN, and no chance of the docs being deleted by the root sync
  • A downloadable PDF: scripts/build-pdf.sh prints the print-optimised learn/guide.html through the browser already on the machine (A4 @page CSS), producing learn/gamehub-guide.pdf for offline reading
  • A CI drift check: the generated site is committed, so the manifests job regenerates it and fails on any diff, and asserts that every document has a page — a generated artifact that is never checked is an artifact that goes stale
  • A load test with a real report: scripts/load-test.js (dependency-free, committed) drives a weighted mix of static, API and probe traffic; docs/load-test.md records the measured numbers for a single t3.micro — including a deliberately pushed run, what the alarms did, and an explicit list of what the test does not prove
  • Erasure verified by a script, not by hand: scripts/verify-gdpr.sh creates a real Cognito user, stores a score, deletes the account through the public API, and asserts that both the row and the identity are gone — cleaning up after itself even when it fails
  • Architecture decisions in one file: docs/decisions.md — 16 decisions in context / decision / consequences / rejected form, each one stating what it costs

Request flow

  1. A user opens GameHub in the browser.
  2. Nginx serves the static frontend files.
  3. JavaScript sends API requests to the frontend's /api/ path.
  4. Nginx forwards those requests to the backend container.
  5. Express processes the request and queries the MySQL container over the private Docker network.
  6. The backend returns JSON, which the frontend uses to render game cards.

Important: The browser accesses the frontend through port 8080. The Nginx container communicates with the backend using Docker networking, and the backend port is not published to the host — the database runs as a local MySQL container (managed by hand, not by IaC — see the note in the Database section).

The browser signs in against Cognito, receives an ID token, and sends it as Authorization: Bearer <token> on every API call. The backend verifies the token's RS256 signature against the pool's public JWKS — the frontend guard is UX, the API is the security boundary.

🚀 Run GameHub Locally

Prerequisites

  • macOS or Linux
  • Git
  • A Docker runtime + Docker Compose (on this Mac: Colima — start it with colima start)

No configuration needed. The stack ships with working local defaults: a MySQL container is seeded automatically from db/init.sql on first start.

1. Clone and bootstrap

git clone https://github.com/cijostany6-bit/GameHub.git
cd GameHub
make bootstrap        # build → start → wait for health → run smoke tests

2. Open GameHub

http://localhost:8080

Useful commands

make ps               # container status (healthy?)
make logs             # tail all logs
make smoke            # re-run the end-to-end checks
make test             # backend unit + integration tests (needs MySQL)
make test-frontend    # game-engine, mapping-contract and auth tests (Node only)
make down             # stop, keep database data
make db-reset         # wipe + re-seed the database
make clean            # full teardown incl. images and DB volume
make kind-up          # same app on a local Kubernetes cluster (kind) → :8081
make argocd-up        # install Argo CD and sync the manifests from Git
make k8s-dbinit       # re-render the Kubernetes DB seed ConfigMap
make learn            # rebuild the /learn docs site and the PDF
make migrate          # apply db/migrations to the running database
make load-test SITE_URL=https://…   # dependency-free load test (see docs/load-test.md)
make verify-gdpr      # verify account deletion end to end (needs a deployment)
make help             # list all targets

Prefer plain Compose? docker-compose up -d --build then ./scripts/smoke.sh does the same.

3. Or run it on Kubernetes

make kind-up     # kind cluster + images + manifests + the same smoke test
make argocd-up   # Argo CD takes over from Git: Synced + Healthy

The cluster publishes the app on http://localhost:8081 so it can run next to the Compose stack on 8080. make kind-down deletes the cluster; the Docker images stay. Everything about it — including what it does not promise — is in docs/step-6-kubernetes-gitops.md.

☁️ Deploy to AWS

Everything is CloudFormation in infra/ — five small stacks, each one a single command. Stack outputs feed the next stack, so there is no spreadsheet of ids to copy by hand.

export AWS_REGION=eu-central-1

# 1. Cognito user pool + app client
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-cognito --template-file infra/cognito.yaml \
  --parameter-overrides Stage=prod

# 2. S3 + CloudFront (deployed first without an API origin)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-site --template-file infra/site.yaml \
  --parameter-overrides Stage=prod

# 3. EC2 host running the compose stack (needs the CloudFront domain)
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-backend --template-file infra/backend.yaml \
  --parameter-overrides \
    Stage=prod \
    CognitoUserPoolId=<pool id> \
    CognitoClientId=<client id> \
    SiteOrigin=<https://cloudfront domain> \
    DbPassword=<16+ chars> RootDbPassword=<16+ chars>

# 4. Re-deploy the site stack with the API origin attached, then publish
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-site --template-file infra/site.yaml \
  --parameter-overrides Stage=prod BackendOriginDomain=<ec2 public dns>

AWS_REGION=$AWS_REGION ./scripts/deploy-frontend.sh

# 5. Observability: log groups + retention, metrics from logs, the synthetic
#    check, eight alarms and the dashboard. AlarmEmail is optional — without it
#    the SNS topic is still created and can be subscribed later (see the
#    TopicArn output), it just has no subscriber yet.
aws cloudformation deploy --region "$AWS_REGION" \
  --stack-name gamehub-observability --template-file infra/observability.yaml \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    Stage=prod \
    InstanceId=<ec2 instance id> \
    SiteUrl=<https://cloudfront domain> \
    AlarmEmail=<you@example.com>

Deploy the observability stack before the host's CloudWatch agent writes its first log line: the template owns the log groups so their retention is set, and an agent-created group would make that resource fail with AlreadyExists.

For continuous deployment, deploy the fourth stack (infra/github-oidc.yaml) once, then set these GitHub repository variables and push to main — the deploy workflow does the rest through OIDC, with no AWS keys stored anywhere:

AWS_REGION, AWS_DEPLOY_ROLE_ARN, SITE_BUCKET, DISTRIBUTION_ID, INSTANCE_ID, COGNITO_USER_POOL_ID, COGNITO_CLIENT_ID.

The workflow does not run on the push itself. It runs when CI succeeds on main (workflow_run + conclusion == 'success') and checks out the commit CI tested, so production never receives a commit that has not been judged. The rollout then pulls the revision on the host, rebuilds the containers, waits for MySQL and applies pending migrations (./scripts/migrate.sh) before a final job smoke-tests the public CloudFront URL — homepage, all 12 catalogue entries, game details and a 401 from an unauthenticated /api/me.

Cost note (honest): the site (S3 + CloudFront), Cognito and the four CloudFormation stacks are inside the free tier at this traffic level. The EC2 instance is the only line item: this account is on a free plan, so AWS rejects instance types that are not free-tier eligible (t2.micro failed with "not eligible for Free Tier") — the stack therefore defaults to t3.micro. On a non-free-tier account that is roughly $8/month. Tear everything down with aws cloudformation delete-stack in reverse order.

🔌 Backend API

The following endpoints are implemented in the current application.

MethodEndpointPurpose
GET/api/healthLiveness — process is up (never touches the database)
GET/api/readyReadiness — database reachable, safe to route traffic (503 otherwise)
GET/api/gamesRetrieve games from the database
GET/api/games/:idSingle game (powers the runner); 404 for unknown and non-numeric ids
GET/api/meEchoes the verified Cognito identity — proof the token was checked
POST/api/scoresStores the player's best score for a game (upsert, GREATEST) — 201 with the stored best
GET/api/scores/meEvery stored row for the caller: the access/portability answer
DELETE/api/meErasure — deletes the caller's scores and their Cognito identity; 204, or 502 if only half of it worked

The API is reachable only through the nginx proxy on :8080 — port 3000 is deliberately not published to the host (use docker-compose exec backend … if you need direct access from inside the network).

Auth behaviour: middleware on every /api/* route except the two probes. If the Cognito pool is configured (that is: in the deployment), requests without a valid ID token get 401 {"error":"Unauthorized"}. If it is not configured (local development), the read-only routes keep working, the identity echo answers 401, and the signed-in features answer 501 rather than pretending — the backend also logs auth_disabled at boot, so the bypass is never silent.

curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl http://localhost:8080/api/games
curl http://localhost:8080/api/games/4

# with the pool configured, protected routes need the ID token:
curl -H "Authorization: Bearer $ID_TOKEN" http://localhost:8080/api/me
curl -H "Authorization: Bearer $ID_TOKEN" http://localhost:8080/api/scores/me
curl -H "Authorization: Bearer $ID_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"game":"Cyber Strike","score":42}' \
     http://localhost:8080/api/scores

# erasure (irreversible — it deletes the Cognito user as well):
curl -X DELETE -H "Authorization: Bearer $ID_TOKEN" http://localhost:8080/api/me

Or run the full check suite: make smoke.

🗄️ Database

GameHub uses MySQL 8.4 in a container, seeded automatically from db/init.sql on the first start of an empty volume. This makes a fresh clone reproducible with no cloud account and no secrets — and the deployed stack runs the same container on the EC2 host, so there is exactly one database setup to reason about. Moving to RDS (multi-AZ, automated backups, managed patching) is a deliberate cost/ops trade-off left for a later phase rather than a claim made here.

Reset to a clean seeded state any time with make db-reset.

The games table contains these fields:

ColumnPurpose
idGame identifier
nameGame title
categoryCategory used by the frontend filters
descriptionShort game description

Sample categories include Action, Racing, and Strategy.

Player data (personal_bests)

ColumnPurpose
user_subThe Cognito sub — never the email address
gameGame name (validated against games.name, so no free-text rows)
scoreThe best score only (GREATEST() on conflict)
updated_atWhen that best was last improved

The primary key is (user_sub, game): one row per player per game, which is the whole data-minimisation argument. Players are identified to the database by a pseudonymous Cognito sub; no email, no name, no IP is stored next to a score.

Migrations

db/init.sql runs once, on an empty data volume — which is correct for a fresh clone and wrong for a live database. Schema changes therefore ship as migrations:

./scripts/migrate.sh            # apply everything pending
./scripts/migrate.sh --status   # what is applied, what is pending

Each file in db/migrations/ is recorded in a schema_migrations ledger with a checksum. A migration that was applied and then edited is refused, because the database that ran it is no longer described by the file. The runner reaches MySQL through docker compose exec on a host and through the mysql client in CI (MIGRATE_VIA), so the same script runs in both places. It is also part of the deploy: the rollout brings the schema up to date after the containers start.

The frontend retrieves game records dynamically through the Express API rather than relying entirely on hardcoded game cards.

🔐 Security Practices

  • No secrets required for local development — compose defaults live in the private Docker network; nothing sensitive exists in the repo.
  • .env is excluded from Git and from image builds (backend/.dockerignore); backend/.env.example documents every variable.
  • The backend runs as a non-root user and reads all configuration from environment variables (12-factor).
  • The API port is not published to the host — only nginx on :8080 is reachable.
  • npm ci from a committed lockfile; the dependency tree is audited (0 vulnerabilities at the time of writing).

Live deployment hardening:

  • JWT verification instead of trust: the API validates the Cognito ID token's RS256 signature against the pool's JWKS using node:crypto (no SDK), then checks iss, aud/client_id, exp and token_use. A forged, expired, wrong-pool or non-ID token is a 401
  • Session expiry is enforced client- and server-side: the guard treats an expired token as signed out, and the API would reject it anyway
  • No SSH on the EC2 host: port 22 is not opened at all; the security group allows 8080 only from the AWS-managed CloudFront origin-facing prefix list, and administration happens through SSM Session Manager / Run Command
  • IMDSv2 required, one-hop response limit, and an encrypted gp3 root volume
  • No long-lived AWS credentials: GitHub Actions assumes a role via OIDC that is scoped to this repository, this bucket, this distribution and this instance
  • Runtime secrets stay on the host: the deployed stack's Cognito ids, CORS origin and database passwords are written into a root-only .env by the CloudFormation user data script — never in Git, never in an image, and the passwords are NoEcho parameters in the stack
  • CloudFront enforces HTTPS for viewers, and the S3 bucket is private with a bucket policy that only permits that distribution (OAC)
  • One AWS permission, one ARN: the instance role's inline policy allows cognito-idp:AdminDeleteUser on the GameHub user pool and nothing else — no CognitoPowerUser, no * resource
  • No third-party requests from the browser: fonts are self-hosted (OFL), so loading a page discloses no visitor IP to Google or to an analytics/CDN provider. This is a German data-protection requirement in practice, not a performance preference

Data protection (GDPR)

  • Data minimisation by schema: one (user_sub, game) row per player holding the best score — no play history, no email in the score table, no IP next to a score
  • Storage limitation: access logs are retained for 7 days and then deleted automatically; the retention is set on the log groups in infra/observability.yaml and the reason is written down in the notice
  • Erasure (Art. 17): DELETE /api/me removes the database rows and the Cognito identity. The order matters — rows first — because if the identity were deleted first, a failure would leave data nobody (including the user) could ever delete. A Cognito failure returns 502 with a truthful message
  • Access & portability (Art. 15, 20): the account page lists the identity and every stored row, with a one-click JSON export
  • Transparency (Art. 13): frontend/privacy.html is a bilingual inventory — item, purpose, legal basis, retention, processors (AWS, eu-central-1) and rights
  • Not stored on purpose: passwords (Cognito holds a salted hash we never see), advertising identifiers, behavioural profiles, third-party analytics

Supply chain & pipeline

  • SBOM per build: an SPDX JSON inventory (syft) is generated in CI and kept as a build artifact
  • Two vulnerability scans, two questions: Trivy over the filesystem (source and dependencies) and over the built image (what the base image adds), plus npm audit — all failing the job on CRITICAL/HIGH
  • Secret scanning over history, not just the diff: gitleaks runs against the full git history, because a secret that was committed and removed is still leaked
  • Dependabot for npm, GitHub Actions and base images: updates arrive as reviewable pull requests that must pass the same CI, with no auto-merge
  • The deploy is gated on CI, not on the push: .github/workflows/deploy.yml triggers on a successful CI run for a specific commit and checks out that commit, so a merge cannot reach production before the tests have judged it
  • Post-deploy verification against the public URL: the pipeline finishes by checking the homepage, all 12 catalogue entries through the API, game details by id, and that an unauthenticated /api/me returns 401 — the edge, not just the host
  • Branch protection on main: the four CI jobs are required status checks in strict mode, administrators are not exempt, force-pushes and branch deletion are disabled, and unresolved conversations block the merge. The gate is only a gate if the merge itself is gated

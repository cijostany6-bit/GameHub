Step 5 — Observability ✅ (2026-10-19)

Verified by: the CloudWatch agent running on the live host, structured JSON nginx access logs arriving in /gamehub/prod/nginx-access, the synthetic canary invoked by hand and by schedule, alarms listed in OK/INSUFFICIENT_DATA with a real target, and one dashboard (gamehub-prod) whose log widgets return rows.

What was built

A deployment you cannot see is a deployment you cannot run. This step makes the live system observable from the outside in and the inside out.

Things that had to be got right

  1. TreatMissingData is a decision, not a default. For the host metrics, missing data is notBreaching — a stopped agent should not page anyone. For the synthetic check it is breaching: no data means the checker itself is broken, and an availability monitor that fails silently is worse than none.
  2. The agent must not create the log groups. If the agent starts first, the groups exist without retention and CloudFormation's AWS::Logs::LogGroup fails with AlreadyExists on the next deploy. The template owns the groups; the agent only writes into them.
  3. A metric filter is not a log parser you can debug in place. Pattern syntax errors produce an alarm that never fires — no warning, no log entry. The check that matters is a manual canary invocation followed by get-metric-statistics, proving a data point exists, not that the template was accepted.
  4. *Metric dimensions must match exactly.* CWAgent attaches InstanceId, and the disk plugin adds path, device and fstype on top. An alarm whose dimension set is one key short sits in INSUFFICIENT_DATA forever. The dimensions in this stack were read back from list-metrics on the running host, then written into the template — verified, not guessed.
  5. The synthetic check measures the path a user takes. It calls the CloudFront URL, not localhost — otherwise it proves the host is alive while the CDN is broken, which is exactly the failure it is meant to catch.
  6. Alarms without a subscriber are half a feature. The topic is created and exported; subscribing is one aws sns subscribe because the account's own contact address cannot be read by an alarm template. Documented in docs/runbook.md §8 rather than pretended away.
  7. Latency is measured where the user waits. $request_time includes the upstream Express call; $upstream_time alone would hide the time nginx spends. Having both on the log line is what lets the runbook split "slow app" from "slow edge" with one query.

Concepts to understand cold

  • The four golden signals — latency, traffic, errors, saturation — and why this dashboard is organised as exactly those four plus availability
  • Metric filters and JSON patterns — how a log line becomes a time series, including extracting a numeric value from a field ($.request_time)
  • Extended statistics — why the p99 alarm exists next to the average, and why an average latency is the metric that hides the outage
  • Error budgets — the shift from "uptime is good" to "the budget decides what we work on next", and what burning 3 h 39 m of a 30-day window means
  • Pull vs push monitoring — why the synthetic check lives outside the system it watches, in a different service, in a different failure domain
  • Retention and cost of observability — log ingestion is the subscription trap of cloud monitoring; retention is an architectural choice

Interview questions this unlocks

  1. "How do you know your service is up right now?" (external synthetic check on the public URL, every 5 minutes, with TreatMissingData: breaching — and what that costs, which is nothing)
  2. "Walk me through an incident: the p99 latency alarm fired. What do you do?" (runbook §3: split request_time vs upstream_time, then CPU credits, then MySQL swap)
  3. "How do you get metrics out of a system you did not instrument?" (structured JSON logs → metric filters, versus adding an SDK or an EMF library)
  4. "Your alarm fired at 03:00. Was it a false positive, and how would you know?" (dimension sets, TreatMissingData, evaluation periods — and the manual canary invocation that proves the wiring)
  5. "What does your error budget buy you, and who decided the target?" (99.5 % on a single-AZ t3.micro is the honest ceiling; the budget decides whether the next sprint is features or reliability)
